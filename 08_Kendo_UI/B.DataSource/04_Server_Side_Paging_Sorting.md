
# 04 — Server-Side Paging, Sorting & Filtering

---

## 🎯 One-Line Definition

> **Server-side operations mean the server does the heavy lifting — it receives what the user asked for (page 2, sorted by name, filtered by IT) and returns only the matching rows, not everything.**

---

## 🤔 The Core Problem — Why Server-Side Matters

Imagine your Employees table has  **50,000 rows** .

```
CLIENT-SIDE (serverPaging: false):
───────────────────────────────────────────────────────
Browser requests data
    │
    ▼
Server sends ALL 50,000 rows at once
    │
    ▼
Browser loads 50,000 rows into memory
Browser does the paging / sorting / filtering itself
    │
    ▼
Problems:
  ✗ Page takes 8 seconds to load
  ✗ Browser uses huge memory
  ✗ Network transfer is massive
  ✗ User waits and waits
```

```
SERVER-SIDE (serverPaging: true):
───────────────────────────────────────────────────────
Browser requests page 1, sorted by Name, filtered by IT
    │
    ▼
Server queries DB with those exact params
Server returns ONLY 10 matching rows
    │
    ▼
Browser loads 10 rows
Grid shows 10 rows
    │
    ▼
  ✓ Page loads instantly
  ✓ Minimal memory
  ✓ Tiny network transfer
  ✓ Scales to millions of rows
```

## 🔑 Enabling Server-Side Operations

Three settings, all together:

```javascript
var dataSource = new kendo.data.DataSource({
    transport: {
        read: { url: "/Employee/Read", type: "POST" }
    },
    schema: {
        data:  "Data",
        total: "Total"   // ← required for server-side paging
    },
    pageSize:        10,
    serverPaging:    true,   // server handles paging
    serverSorting:   true,   // server handles sorting
    serverFiltering: true    // server handles filtering
});
```

In Tag Helper (Kendo Grid):

```cshtml
<kendo-grid name="employeeGrid">

    <datasource type="DataSourceTagHelperType.Ajax"
                page-size="10"
                server-paging="true"
                server-sorting="true"
                server-filtering="true">
        <transport>
            <read url="@Url.Action("Read", "Employee")" type="POST" />
        </transport>
        <schema>
            <model id="Id" />
        </schema>
    </datasource>

    <pageable />
    <sortable enabled="true" />
    <filterable enabled="true" />

</kendo-grid>
```

## 🔑 What Kendo Sends to the Server

When the user clicks page 2, sorts by Salary descending, and filters Department = IT, Kendo sends this in the POST body:

```
page=2
pageSize=10
sort[0][field]=Salary
sort[0][dir]=desc
filter[logic]=and
filter[filters][0][field]=Department
filter[filters][0][operator]=eq
filter[filters][0][value]=IT
```

`[DataSourceRequest]` reads all of this automatically. You never parse it manually.

---

## 🔑 The Controller — `[DataSourceRequest]` and `ToDataSourceResult`

```csharp
[HttpPost]
public JsonResult Read([DataSourceRequest] DataSourceRequest request)
{
    var result = _db.Employees
                    .AsQueryable()            // IQueryable — not yet executed
                    .ToDataSourceResult(request);  // applies page/sort/filter → hits DB

    return Json(result);
}
```

What `ToDataSourceResult` does internally:

```
Your IQueryable<Employee>
    │
    ├─► Applies WHERE  (from filter)    → WHERE Department = 'IT'
    ├─► Applies ORDER BY (from sort)    → ORDER BY Salary DESC
    ├─► Counts total matching rows      → SELECT COUNT(*) → 12
    ├─► Applies SKIP/TAKE (from page)   → SKIP 10 TAKE 10  (page 2)
    └─► Returns { Data: [10 rows], Total: 12 }
```

This all becomes one efficient SQL query — it does NOT load all rows into memory first.

## 🔑 Why `schema.total` is Non-Negotiable for Paging

The Grid needs to know **how many total pages to show** in the pager at the bottom.

```
Without schema.total:          With schema.total:
──────────────────────         ──────────────────────────────
Grid gets 10 rows              Grid gets 10 rows
Grid thinks there are          Grid knows Total = 47
only 10 total records          Grid shows: Page 1 of 5
Shows: Page 1 of 1             Pager shows 5 page buttons
No next page button            User can navigate ✓
```

```javascript
schema: {
    data:  "Data",   // "records are in response.Data"
    total: "Total"   // "total count is in response.Total" ← pager needs this
}
```

Your controller's `ToDataSourceResult` populates `Total` automatically.

## 🔑 Sorting — Single and Multi-Column

### Single column sort (user clicks one column header)

```
Kendo sends:
  sort[0][field]=Name
  sort[0][dir]=asc

SQL generated by ToDataSourceResult:
  ORDER BY Name ASC
```

### Multi-column sort (user holds Shift and clicks a second column)

```
Kendo sends:
  sort[0][field]=Department
  sort[0][dir]=asc
  sort[1][field]=Salary
  sort[1][dir]=desc

SQL generated:
  ORDER BY Department ASC, Salary DESC
```

Kendo handles multi-sort automatically — you don't write any extra code.

## 🔑 Filtering — Operators Reference

When a user applies a filter in the Grid, Kendo sends an `operator` field. These are the operators and what SQL they produce:

| Kendo Operator     | What User Selected          | SQL Equivalent      |
| ------------------ | --------------------------- | ------------------- |
| `eq`             | is equal to                 | `= 'IT'`          |
| `neq`            | is not equal to             | `<> 'IT'`         |
| `contains`       | contains                    | `LIKE '%IT%'`     |
| `doesnotcontain` | does not contain            | `NOT LIKE '%IT%'` |
| `startswith`     | starts with                 | `LIKE 'IT%'`      |
| `endswith`       | ends with                   | `LIKE '%IT'`      |
| `gt`             | is greater than             | `> 50000`         |
| `gte`            | is greater than or equal to | `>= 50000`        |
| `lt`             | is less than                | `< 50000`         |
| `lte`            | is less than or equal to    | `<= 50000`        |
| `isnull`         | is null                     | `IS NULL`         |
| `isnotnull`      | is not null                 | `IS NOT NULL`     |

`ToDataSourceResult` maps all of these to the correct SQL automatically.

## 🔑 Adding Your Own Filter ON TOP of Kendo's

A very common real-world need: the grid always filters by the  **currently logged-in user's company** , plus whatever filter the user adds themselves.

```csharp
[HttpPost]
public JsonResult Read([DataSourceRequest] DataSourceRequest request)
{
    // Start with a base query — your mandatory filter
    var query = _db.Employees
                   .Where(e => e.CompanyId == GetCurrentUserCompanyId())
                   .Where(e => e.IsDeleted == false);   // soft delete

    // Then let Kendo apply its paging/sorting/filtering on top
    return Json(query.ToDataSourceResult(request));
}
```

The user's grid filter applies on top of your server filter — Kendo combines them correctly.

## 🔑 Client-Side vs Server-Side — Decision Table

| Scenario                                 | Use            |
| ---------------------------------------- | -------------- |
| Data has more than ~500 rows             | Server-side ✅ |
| Data is from a database                  | Server-side ✅ |
| Need accurate total count for pager      | Server-side ✅ |
| Data is a small static list (< 200 rows) | Client-side ✅ |
| Data is already loaded on the page       | Client-side ✅ |
| Simple dropdown with fixed options       | Client-side ✅ |

## ⚠️ Common Mistakes

| Mistake                                          | What Happens                                       | Fix                                                 |
| ------------------------------------------------ | -------------------------------------------------- | --------------------------------------------------- |
| `serverPaging: true`but no `schema.total`    | Pager shows only 1 page regardless of data         | Add `schema: { total: "Total" }`                  |
| Using `.ToList()`before `ToDataSourceResult` | All rows loaded into memory — defeats server-side | Pass `IQueryable`, not `IEnumerable`or `List` |
| `serverPaging: true`but `schema.data`missing | Grid shows 0 rows                                  | Add `schema: { data: "Data" }`                    |
| Sorting a navigation property directly           | Runtime error                                      | Project to a flat DTO first, then sort              |

### The IQueryable vs IEnumerable trap — most important

```csharp
// ❌ WRONG — loads all rows into memory FIRST, then pages
var employees = _db.Employees.ToList();            // executes SQL, all rows in RAM
return Json(employees.ToDataSourceResult(request)); // paging done in memory

// ✅ CORRECT — SQL query is built first, then executed with page/sort/filter
var employees = _db.Employees.AsQueryable();        // no SQL yet
return Json(employees.ToDataSourceResult(request)); // one efficient SQL query
```

## ❓ Interview Questions

**Q: What is the difference between server-side and client-side paging?**

> Server-side paging sends only the requested page of data from the server (e.g., 10 rows). Client-side paging loads all records at once and the browser handles pagination. Server-side is required for large datasets; client-side is fine for small static lists.

**Q: Why must you pass `IQueryable` to `ToDataSourceResult` instead of `IEnumerable`?**

> `ToDataSourceResult` uses LINQ expression trees to build an efficient SQL query with WHERE, ORDER BY, and SKIP/TAKE. If you pass a `List` or call `.ToList()` first, all data is already in memory and the server-side operations lose their benefit.

**Q: How does Kendo know the total number of pages?**

> From `schema.total` — the DataSource reads the `Total` property from the JSON response and uses it to calculate how many page buttons to show. Without it, the Grid thinks there is only one page.

**Q: Can you add your own filter on top of the Kendo filter?**

> Yes. Apply your mandatory conditions to the `IQueryable` first (e.g., filter by current user's company), then pass it to `ToDataSourceResult`. Kendo's filter applies on top of yours, and the SQL combines both.
