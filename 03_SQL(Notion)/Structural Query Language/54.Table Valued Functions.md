
# 54.Table Valued Functions

---

## 📌 What is a Table Valued Function (TVF)

> A **Table Valued Function (TVF)** is a user-defined function that
> returns a **table** (a full result set with rows and columns) instead
> of a single value — usable directly in a `FROM` clause, like a table.

```
Scalar Function          → returns ONE value        → usable in SELECT/WHERE
Table Valued Function     → returns a TABLE            → usable in FROM/JOIN, like a view
```

There are two kinds:

- **Inline TVF (ITVF)** — a single `RETURN (SELECT ...)`, no BEGIN/END body
- **Multi-statement TVF (MSTVF)** — has a `BEGIN...END` body, builds the table step-by-step

---

## 📌 Inline Table-Valued Function (ITVF)

> The simpler, **faster** type — essentially a **parameterized view**.
> Just one `RETURN` with a single `SELECT` statement.

```sql
CREATE FUNCTION dbo.fn_GetOrdersByUser (@UserId NVARCHAR(50))
RETURNS TABLE
AS
RETURN
(
    SELECT OrderId, Amount, OrderDate
    FROM Orders
    WHERE UserId = @UserId
);
```

**Using it — call it in FROM, just like a table:**

```sql
SELECT * FROM dbo.fn_GetOrdersByUser('sumit');

-- Can be filtered, joined, ordered like any table
SELECT OrderId, Amount
FROM dbo.fn_GetOrdersByUser('sumit')
WHERE Amount > 1000
ORDER BY OrderDate DESC;

-- Can even be used in a JOIN, passing a column as the parameter
SELECT U.UserId, O.OrderId, O.Amount
FROM Users U
CROSS APPLY dbo.fn_GetOrdersByUser(U.UserId) O;
```

> 🔑 **CROSS APPLY** is how you join a TVF **per row** of another table
> — passing each row's value as the function's parameter. `OUTER APPLY`
> is the LEFT JOIN equivalent (keeps rows even if the function returns
> nothing).

---

## 📌 Multi-Statement Table-Valued Function (MSTVF)

> Has a `BEGIN...END` body — you explicitly `DECLARE` a table variable,
> populate it with `INSERT`, then `RETURN`. Allows more complex logic
> (loops, multiple steps) but is **slower** than an inline TVF.

```sql
CREATE FUNCTION dbo.fn_GetUserRiskReport (@MinFailedAttempts INT)
RETURNS @Result TABLE
(
    UserId NVARCHAR(50),
    FailedAttempts INT,
    RiskLevel NVARCHAR(10)
)
AS
BEGIN
    INSERT INTO @Result (UserId, FailedAttempts, RiskLevel)
    SELECT
        UserId,
        FailedAttempts,
        CASE
            WHEN FailedAttempts >= 5 THEN 'High'
            WHEN FailedAttempts >= 2 THEN 'Medium'
            ELSE 'Low'
        END
    FROM Users
    WHERE FailedAttempts >= @MinFailedAttempts;

    RETURN;
END;
```

```sql
SELECT * FROM dbo.fn_GetUserRiskReport(2);
```

## 📌 Inline TVF vs Multi-Statement TVF

|                            | Inline TVF (ITVF)                                                            | Multi-Statement TVF (MSTVF)                                                         |
| -------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Body                       | Single`RETURN (SELECT...)`                                                 | `BEGIN...END` with explicit table variable                                        |
| Performance                | ⚡ Fast — optimizer treats it like a view, can use indexes on source tables | 🐢 Slower — treated as a "black box", often estimates only 1 row (bad query plans) |
| Complexity allowed         | Simple: one query                                                            | Complex: loops, multiple INSERTs, branching                                         |
| Optimizer can "see inside" | ✅ Yes — merges into the outer query plan                                   | ❌ No — executes somewhat in isolation                                             |
| Recommended for            | Most cases — prefer this by default                                         | Only when logic genuinely needs multiple steps                                      |

> 🔑 **Rule of thumb:** always prefer an **Inline TVF** over a
> Multi-Statement TVF when possible — the performance difference on
> larger tables can be significant because MSTVFs historically confuse
> the query optimizer's row-count estimates.

---

## 📌 TVF vs View vs Scalar Function vs Stored Procedure

|                              | TVF     | View              | Scalar Function | Stored Procedure               |
| ---------------------------- | ------- | ----------------- | --------------- | ------------------------------ |
| Returns                      | A table | A table (virtual) | One value       | Result sets / OUTPUT / nothing |
| Accepts parameters           | ✅ Yes  | ❌ No             | ✅ Yes          | ✅ Yes                         |
| Usable in FROM/JOIN          | ✅ Yes  | ✅ Yes            | ❌ No           | ❌ No                          |
| Usable in SELECT column list | ❌ No   | ❌ No             | ✅ Yes          | ❌ No                          |
| Called with EXEC             | ❌ No   | ❌ No             | ❌ No           | ✅ Yes                         |

> 🔑 **Think of an Inline TVF as "a View that accepts parameters"** —
> that's the single biggest reason to reach for one: a View can't take
> a `WHERE UserId = @X` parameter, but a TVF can.

## 📌 Real-World Example — Parameterized Reporting

```sql
-- Reusable, parameterized "top N orders" logic
CREATE FUNCTION dbo.fn_GetTopOrders (@UserId NVARCHAR(50), @TopN INT)
RETURNS TABLE
AS
RETURN
(
    SELECT TOP (@TopN) OrderId, Amount, OrderDate
    FROM Orders
    WHERE UserId = @UserId
    ORDER BY Amount DESC
);
```

```sql
-- Different callers, different parameters — same reusable logic
SELECT * FROM dbo.fn_GetTopOrders('sumit', 5);
SELECT * FROM dbo.fn_GetTopOrders('rahul', 10);

-- Used per-user across a whole table with CROSS APPLY
SELECT U.UserId, T.OrderId, T.Amount
FROM Users U
CROSS APPLY dbo.fn_GetTopOrders(U.UserId, 3) T;
```

## 📌 Common Pitfalls

| Pitfall                                                              | Fix                                                                                                      |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Defaulting to Multi-Statement TVF out of habit                       | Prefer Inline TVF whenever the logic is a single query                                                   |
| Forgetting`CROSS APPLY`/`OUTER APPLY` when joining a TVF per-row | Regular`JOIN` doesn't work when the TVF parameter comes from the other table's column — use `APPLY` |
| Assuming a TVF can modify data                                       | TVFs are read-only, just like scalar functions — use a stored procedure to write data                   |
| Complex MSTVF causing bad query plans on large data                  | Consider rewriting as an Inline TVF, or use a temp table + stored procedure instead                      |

## ❓ Interview Questions

**Q: What's the difference between an Inline TVF and a Multi-Statement TVF?**
A: An Inline TVF has a single RETURN with one SELECT statement, and the optimizer can merge it into the calling query's plan — similar to a view, and generally fast. A Multi-Statement TVF has a BEGIN...END body with an explicit table variable that's populated via INSERT, allowing more complex logic, but it's treated as a black box by the optimizer and can produce poor query plans on larger tables.

**Q: How is a TVF different from a View?**
A: A View cannot accept parameters, while a TVF can — making a TVF effectively a "parameterized view." Both are used in a FROM clause and return a table-shaped result.

**Q: What is CROSS APPLY used for with TVFs?**
A: CROSS APPLY lets you call a table-valued function once per row of another table, passing that row's column value in as the function's parameter — something a regular JOIN can't do since a JOIN's ON condition can't invoke a function per outer row.

**Q: Why is an Inline TVF generally recommended over a Multi-Statement TVF?**
A: Because the SQL Server optimizer can "see inside" an inline TVF and merge its logic with the outer query — potentially using indexes and generating accurate row estimates. A multi-statement TVF is opaque to the optimizer, often assumed to return just one row regardless of actual data volume, which can lead to inefficient execution plans.
