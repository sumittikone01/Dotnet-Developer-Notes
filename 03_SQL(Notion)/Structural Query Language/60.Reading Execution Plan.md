
# 60.Reading Execution Plan

---

## 📌 What is an Execution Plan

> An **Execution Plan** is SQL Server's **map of exactly how it plans to
> run your query** — which indexes it uses (or doesn't), what order it
> joins tables in, and where the time/cost is spent. Reading it is the
> #1 skill for diagnosing "why is this query slow?"

```
Estimated Execution Plan  → SQL Server's PREDICTION before running
                             (based on statistics, doesn't actually execute)

Actual Execution Plan     → The REAL plan used, WITH real row counts,
                             after actually running the query
```

---

## 📌 Getting an Execution Plan in SSMS

| Shortcut                              | Shows                                                                 |
| ------------------------------------- | --------------------------------------------------------------------- |
| `Ctrl + L`                          | **Estimated** Execution Plan — doesn't run the query           |
| `Ctrl + M`, then run query (`F5`) | **Actual** Execution Plan — runs the query, shows real numbers |

> 🔑 **Always prefer the Actual plan when possible** — the Estimated
> plan's row-count guesses can be wrong (outdated statistics, complex
> predicates), and those wrong guesses are often the root cause of a
> slow query.

---

## 📌 Reading the Plan — General Flow

```
Execution plans read RIGHT TO LEFT, and BOTTOM TO TOP.
──────────────────────────────────────────
The right-most / bottom-most operator runs FIRST
(usually reading a table or index),
then data flows LEFT/UP through each operator,
until the final result appears at the top-left (SELECT icon).
```

```
[SELECT]  ← final result, top-left
   ↑
[Nested Loop Join]
   ↑                    ↑
[Index Seek: Users]   [Index Seek: Orders]  ← these run FIRST (rightmost)
```

---

## 📌 Key Icons/Operators to Recognize

| Operator                       | Meaning                                                                | Good or Bad?                                    |
| ------------------------------ | ---------------------------------------------------------------------- | ----------------------------------------------- |
| **Table Scan**           | Reads every row in the table (no useful index)                         | 🔴 Usually bad on large tables                  |
| **Clustered Index Scan** | Reads every row via the clustered index (same problem, different name) | 🔴 Usually bad on large tables                  |
| **Index Seek**           | Jumps directly to matching rows using an index                         | 🟢 Good                                         |
| **Key Lookup**           | Extra trip back to the table for columns not in the index used         | 🟡 OK occasionally, bad if repeated many times  |
| **Nested Loop Join**     | For each row in one table, loop through matches in the other           | 🟢 Good for small row counts                    |
| **Hash Match Join**      | Builds a hash table in memory to match rows                            | 🟡 OK for large unsorted sets, but memory-heavy |
| **Merge Join**           | Both inputs already sorted, merges them in one pass                    | 🟢 Good — fastest join type when applicable    |
| **Sort**                 | Explicitly sorting data (e.g. for ORDER BY without a helpful index)    | 🟡 Watch for — can be expensive on large sets  |

## 📌 The Most Important Number — Row Count Mismatch

> Hovering over any operator in an **Actual** plan shows **Estimated
> Number of Rows** vs **Actual Number of Rows**. A big mismatch is one
> of the most common causes of a bad, slow plan.

```
Operator: Index Seek
Estimated Number of Rows: 10
Actual Number of Rows: 500,000        ← HUGE mismatch!
```

> When estimated and actual differ wildly, SQL Server likely chose the
> **wrong join type or wrong index** based on bad assumptions. Common
> causes: outdated statistics, or a query pattern the optimizer can't
> estimate well (e.g. a scalar function wrapping a column).

```sql
-- Fix outdated statistics
UPDATE STATISTICS Users;

-- Or update stats for the whole database
EXEC sp_updatestats;
```

---

## 📌 Cost Percentages — Where to Focus

> Each operator shows a **"Cost: X%"** relative to the whole query.
> Focus your tuning effort on the operator(s) with the **highest
> percentage** — that's where the time is actually going.

```
[SELECT]
   ↑
[Hash Match Join]  Cost: 5%
   ↑                    ↑
[Index Seek: Users]   [Table Scan: Orders]  Cost: 85%   ← THIS is the problem
                        Cost: 10%
```

> In this example, don't waste time tuning the `Users` seek — the
> `Orders` Table Scan is where 85% of the cost lives. Adding an
> appropriate index on `Orders` is the actual fix.

---

## 📌 Missing Index Suggestions

> SSMS often shows a **green, dashed "Missing Index" suggestion**
> directly in the execution plan — right-click it to script the
> `CREATE INDEX` statement it recommends.

```sql
-- Example of what SSMS might suggest, based on your query pattern
CREATE NONCLUSTERED INDEX IX_Orders_UserId
ON Orders (UserId)
INCLUDE (Amount, OrderDate);
```

> ⚠️ **Don't blindly create every suggested index** — SSMS suggests
> based on a single query in isolation. Too many indexes hurts write
> performance (see Indexes Overview). Evaluate whether the suggestion
> makes sense across your actual workload.

---

## 📌 Warnings in the Plan — Yellow Triangle Icons

> A yellow warning triangle on an operator flags something SQL Server
> wants to call out — hover to see the detail.

| Common Warning                                   | Meaning                                                                                    |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| "Type Conversion may affect CardinalityEstimate" | Implicit conversion is happening — comparing mismatched data types, can block index usage |
| "No Join Predicate"                              | A JOIN with no ON condition — accidental CROSS JOIN, usually a mistake                    |
| "Excessive memory grant"                         | Query requested much more memory than it used — indicates bad estimates                   |

## 📌 Real Example — Diagnosing a Slow Query

```sql
-- Slow query with a scalar function in WHERE
SELECT UserId, Email FROM Users
WHERE dbo.fn_GetRiskLevel(FailedAttempts) = 'High';
```

**Execution plan shows:**

```
[SELECT]
   ↑
[Clustered Index Scan: Users]   Cost: 98%
   Estimated Rows: 100   Actual Rows: 4,231,000   ← massive mismatch!
```

**Diagnosis:** The scalar function prevents SQL Server from estimating
accurately or using an index — it has to scan and evaluate the function
on every row.

**Fix — inline the logic:**

```sql
SELECT UserId, Email FROM Users
WHERE FailedAttempts >= 5;

-- With a supporting index:
CREATE INDEX IX_Users_FailedAttempts ON Users (FailedAttempts) INCLUDE (Email);
```

```
New plan:
[SELECT]
   ↑
[Index Seek: IX_Users_FailedAttempts]   Cost: 100% (but query is now milliseconds, not seconds)
```

---

## 📌 Quick Diagnostic Checklist

```
1. Estimated vs Actual → Ctrl+M (actual), run query, compare row counts
2. Find the highest-cost operator → that's where to focus
3. Table Scan / Clustered Index Scan on a large table → likely missing an index
4. Key Lookup appearing many times → consider a Covering Index
5. Estimated vs Actual rows wildly different → check statistics, scalar functions,
   implicit conversions
6. Check for a green "Missing Index" suggestion → evaluate, don't blindly apply
7. Look for yellow warning triangles → hover for the specific issue
```

## ❓ Interview Questions

**Q: What's the difference between an Estimated and an Actual execution plan?**
A: The Estimated plan is SQL Server's prediction based on statistics without actually running the query. The Actual plan runs the query and shows real row counts alongside the estimates, making it more reliable for diagnosing problems — especially when estimated and actual numbers diverge significantly.

**Q: What does a large gap between estimated and actual row counts usually indicate?**
A: That SQL Server's assumptions were wrong when it chose the execution plan — often due to outdated statistics, a function wrapped around a filtered column, or an implicit data type conversion — leading it to pick a suboptimal join type or access method.

**Q: What is a Key Lookup, and when should you be concerned about seeing one in a plan?**
A: It's an extra step where SQL Server goes back to the clustered index to fetch columns not included in the nonclustered index it used. A single occasional Key Lookup is fine, but seeing it repeated many times (proportional to a high row count) is a strong signal to add a Covering Index with an INCLUDE clause.

**Q: How should you decide which part of a query to optimize first?**
A: Look at the cost percentage shown on each operator in the execution plan and focus on the operator(s) with the highest relative cost — that's where the actual time is being spent, rather than guessing based on how the query "reads."
