## 📌 1. Avoid `SELECT *` — Select Only What You Need

```sql
-- ❌ Pulls every column, defeats covering indexes, more I/O
SELECT * FROM Users WHERE Email = 'sumit@company.com';

-- ✅ Only what's needed — can be fully satisfied by a covering index
SELECT UserId, Role FROM Users WHERE Email = 'sumit@company.com';
```

> `SELECT *` also breaks if columns are added/removed later, and
> transfers unnecessary data over the network.

---

## 📌 2. Never Wrap an Indexed Column in a Function

```sql
-- ❌ Function on the column → can't seek the index on CreatedAt
SELECT * FROM Users WHERE YEAR(CreatedAt) = 2026;

-- ✅ Rewrite as a range — index-friendly
SELECT * FROM Users
WHERE CreatedAt >= '2026-01-01' AND CreatedAt < '2027-01-01';
```

```sql
-- ❌ Function on the column
SELECT * FROM Users WHERE UPPER(Email) = 'SUMIT@COMPANY.COM';

-- ✅ Store/compare consistently, or use a computed+indexed column instead
SELECT * FROM Users WHERE Email = 'sumit@company.com';
```

> This is the single most common "silent index killer" — wrapping any
> column in `WHERE` with a function forces SQL Server to evaluate that
> function on every row (Scan), since it can no longer just look up the
> raw stored value.

---

## 📌 3. Avoid Leading Wildcards in LIKE

```sql
-- ❌ Can't seek — leading % means "search from anywhere in the string"
SELECT * FROM Users WHERE Email LIKE '%company.com';

-- ✅ Can seek — no leading %, SQL Server can jump to matching prefix
SELECT * FROM Users WHERE Email LIKE 'sumit%';
```

> For genuine "contains anywhere" search needs at scale, consider
> **Full-Text Search** instead of `LIKE '%...%'`.

---

## 📌 4. Watch for Implicit Conversions

```sql
-- UserId column is NVARCHAR, but compared to an unquoted number
SELECT * FROM Users WHERE UserId = 12345;
-- ❌ SQL Server implicitly converts EVERY row's UserId to match —
--    silently disables efficient index usage

-- ✅ Match data types exactly
SELECT * FROM Users WHERE UserId = '12345';
```

> Implicit conversions are sneaky — the query still "works" and
> returns correct results, but performance quietly degrades because
> the optimizer can't seek efficiently.

---

## 📌 5. Prefer EXISTS Over COUNT(*) for Existence Checks

```sql
-- ❌ Counts ALL matching rows just to check if > 0 — wasteful
IF (SELECT COUNT(*) FROM Orders WHERE UserId = 'sumit') > 0
    PRINT 'Has orders';

-- ✅ Stops at the FIRST match — much faster
IF EXISTS (SELECT 1 FROM Orders WHERE UserId = 'sumit')
    PRINT 'Has orders';
```

---

## 📌 6. Avoid Unnecessary DISTINCT / ORDER BY

```sql
-- ❌ DISTINCT added out of habit, when duplicates aren't actually possible
SELECT DISTINCT UserId FROM Users;   -- UserId is already unique (PK)!

-- ✅ Remove it — saves an unnecessary sort/dedup operation
SELECT UserId FROM Users;
```

> `DISTINCT` and `ORDER BY` both often force a **Sort** operation —
> only include them when genuinely needed.

---

## 📌 7. JOIN Instead of Correlated Subquery for Aggregates

```sql
-- ❌ Correlated subquery re-runs per outer row
SELECT U.UserId,
    (SELECT COUNT(*) FROM Orders O WHERE O.UserId = U.UserId) AS OrderCount
FROM Users U;

-- ✅ JOIN + GROUP BY — processed in one pass
SELECT U.UserId, COUNT(O.OrderId) AS OrderCount
FROM Users U
LEFT JOIN Orders O ON O.UserId = U.UserId
GROUP BY U.UserId;
```

---

## 📌 8. Filter Early — WHERE Before JOIN When Possible

```sql
-- ❌ Joins the FULL Orders table, then filters
SELECT U.UserId, O.Amount
FROM Users U
INNER JOIN Orders O ON O.UserId = U.UserId
WHERE O.OrderDate >= '2026-01-01';

-- ✅ Same result, but pre-filtering in a subquery/CTE can help the
--    optimizer choose a smaller intermediate set (optimizer often does
--    this automatically, but explicit filtering helps in complex queries)
WITH RecentOrders AS
(
    SELECT UserId, Amount FROM Orders WHERE OrderDate >= '2026-01-01'
)
SELECT U.UserId, R.Amount
FROM Users U
INNER JOIN RecentOrders R ON R.UserId = U.UserId;
```

> Modern SQL Server's optimizer is usually smart enough to push filters
> down automatically — but for complex, multi-join queries, being
> explicit can help, and always makes intent clearer to read.

## 📌 9. Avoid Cursors — Use Set-Based Logic Instead

```sql
-- ❌ Cursor — processes ONE row at a time (RBAR: Row By Agonizing Row)
DECLARE @UserId NVARCHAR(50);
DECLARE cur CURSOR FOR SELECT UserId FROM Users WHERE IsActive = 0;
OPEN cur;
FETCH NEXT FROM cur INTO @UserId;
WHILE @@FETCH_STATUS = 0
BEGIN
    UPDATE Users SET LastCleanup = GETDATE() WHERE UserId = @UserId;
    FETCH NEXT FROM cur INTO @UserId;
END
CLOSE cur; DEALLOCATE cur;

-- ✅ Set-based — handles all matching rows in ONE statement, far faster
UPDATE Users SET LastCleanup = GETDATE() WHERE IsActive = 0;
```

> SQL Server is built for **set-based** operations. Cursors/loops
> should be a last resort — almost anything expressible as a loop can
> be rewritten as a single set-based statement.

---

## 📌 10. Use Parameters, Not String Concatenation

```csharp
// ❌ String concatenation — no plan reuse, SQL injection risk
string sql = "SELECT * FROM Users WHERE UserId = '" + userId + "'";

// ✅ Parameterized — plan gets cached and reused, safe from injection
string sql = "SELECT * FROM Users WHERE UserId = @UserId";
cmd.Parameters.AddWithValue("@UserId", userId);
```

> Beyond security, parameterized queries let SQL Server **reuse the
> cached execution plan** instead of recompiling a "new" query every
> time the literal value changes.

---

## 📌 11. Batch Large DELETE/UPDATE Operations

```sql
-- ❌ Deleting millions of rows in one giant transaction — huge log growth, long locks
DELETE FROM AuditLog WHERE CreatedAt < '2020-01-01';

-- ✅ Batch it — smaller transactions, less log/lock pressure
WHILE 1 = 1
BEGIN
    DELETE TOP (10000) FROM AuditLog WHERE CreatedAt < '2020-01-01';
    IF @@ROWCOUNT = 0 BREAK;
END
```

## 📌 Quick Reference — Optimization Checklist

| Symptom                                    | Fix                                             |
| ------------------------------------------ | ----------------------------------------------- |
| `SELECT *` everywhere                    | Select only needed columns                      |
| Function wrapped around a WHERE column     | Rewrite as a range/raw comparison               |
| `LIKE '%text%'`                          | Avoid leading wildcard, or use Full-Text Search |
| Comparing mismatched data types            | Match types explicitly                          |
| `COUNT(*) > 0` for existence checks      | Use`EXISTS`                                   |
| Unnecessary`DISTINCT`/`ORDER BY`       | Remove if not truly needed                      |
| Correlated subquery computing an aggregate | Rewrite as`JOIN` + `GROUP BY`               |
| Cursor/loop doing row-by-row updates       | Rewrite as one set-based statement              |
| String-concatenated SQL from app code      | Use parameterized queries                       |
| Massive single DELETE/UPDATE               | Batch it with`TOP (n)` in a loop              |

## ❓ Interview Questions

**Q: Why is wrapping a column in a function inside WHERE considered bad practice?**
A: It prevents SQL Server from using an index seek on that column efficiently, because the function must be evaluated for every row before it can be compared — effectively forcing a scan even if a perfectly good index exists on the raw column.

**Q: Why is EXISTS generally preferred over COUNT(*) for existence checks?**
A: EXISTS can stop as soon as it finds a single matching row, while COUNT(*) must tally every matching row even though only whether the count is greater than zero actually matters — making EXISTS more efficient for simple "does this exist" checks.

**Q: Why are cursors generally discouraged in SQL Server?**
A: SQL Server is optimized for set-based operations that process many rows at once. Cursors process one row at a time (sometimes called RBAR — Row By Agonizing Row), which is typically far slower than an equivalent single set-based UPDATE/DELETE/INSERT statement.

**Q: What's the performance benefit of parameterized queries over string-concatenated SQL?**
A: Parameterized queries let SQL Server cache and reuse the same execution plan across calls with different parameter values, avoiding costly recompilation — in addition to eliminating SQL injection risk that string concatenation introduces.
