
# 58.Indexes Overview

---

## 📌 What is an Index

> An **Index** is a separate data structure SQL Server maintains alongside
> a table, built to make **finding rows faster** — the same idea as a
> book's index letting you jump straight to a page instead of reading
> every page.

```
WITHOUT an index:
──────────────────────────────────────────
SELECT * FROM Users WHERE Email = 'x@y.com';
→ SQL Server scans EVERY row in the table (Table Scan) — slow on big tables

WITH an index on Email:
──────────────────────────────────────────
SELECT * FROM Users WHERE Email = 'x@y.com';
→ SQL Server jumps almost directly to the matching row (Index Seek) — fast
```

- Indexes speed up **reads** (SELECT, WHERE, JOIN, ORDER BY)
- Indexes slow down **writes** (INSERT/UPDATE/DELETE) slightly — the index itself must be updated too
- Every table can have **only 1 Clustered Index**, but **many Nonclustered Indexes**

---

## 📌 The Book Analogy

```
Clustered Index    = The book's pages are PHYSICALLY sorted (like a dictionary — 
                      words are in alphabetical order on the actual pages)

Nonclustered Index = A separate index section at the back of the book 
                      that points you to a page number — the book's actual
                      pages aren't reordered
```

> Full detail on Clustered vs Nonclustered is in the next note — this
> note focuses on indexing concepts broadly.

## 📌 Why Indexes Matter — Table Scan vs Index Seek

```sql
-- No index on Email → SQL Server checks every single row
SELECT * FROM Users WHERE Email = 'sumit@company.com';
```

| Without Index                           | With Index                                              |
| --------------------------------------- | ------------------------------------------------------- |
| **Table Scan** — reads every row | **Index Seek** — jumps directly to matching rows |
| Cost grows with table size              | Cost stays roughly flat (logarithmic)                   |
| Fine for tiny tables                    | Essential for large tables                              |

> See the execution plan (`Ctrl+M` in SSMS) to check whether a query is
> doing a Scan (bad on large tables) or a Seek (good).

## 📌 Creating a Basic Index

```sql
-- Syntax
CREATE INDEX IndexName ON TableName (ColumnName);

-- Example: speed up searches/joins on Email
CREATE INDEX IX_Users_Email ON Users (Email);

-- Composite index — multiple columns, order matters (see below)
CREATE INDEX IX_Users_Dept_Role ON Users (Department, Role);

-- Unique index — also enforces uniqueness like a constraint
CREATE UNIQUE INDEX IX_Users_Email_Unique ON Users (Email);
```

---

## 📌 Composite Index — Column Order Matters

> A composite (multi-column) index is only useful for filtering when the
> query's `WHERE`/`JOIN`/`ORDER BY` uses the columns **starting from the
> leftmost** column in the index — this is called the "leftmost prefix" rule.

```sql
CREATE INDEX IX_Users_Dept_Role ON Users (Department, Role);
```

```sql
-- ✅ Uses the index — filters on Department (leftmost column)
SELECT * FROM Users WHERE Department = 'IT';

-- ✅ Uses the index fully — filters on both, in order
SELECT * FROM Users WHERE Department = 'IT' AND Role = 'Admin';

-- ❌ Does NOT use this index efficiently — skips the leftmost column
SELECT * FROM Users WHERE Role = 'Admin';
```

```
Think of it like a phone book sorted by (LastName, FirstName):
──────────────────────────────────────────
✅ "Find everyone named Smith"              → easy, sorted by LastName first
✅ "Find John Smith"                        → easy, both columns in order
❌ "Find everyone named John" (any lastname) → USELESS, book isn't sorted by FirstName
```

## 📌 Included Columns — Covering Indexes

> An index normally only stores the columns it's built on. `INCLUDE` adds
> extra columns to the index **leaf level** (without making them part of
> the sort key) — letting a query be answered **entirely from the index**,
> without touching the actual table.

```sql
CREATE INDEX IX_Users_Email_Covering
ON Users (Email)
INCLUDE (Role, IsActive);
```

```sql
-- This query can be answered 100% from the index — no lookup to the table needed
SELECT Email, Role, IsActive FROM Users WHERE Email = 'sumit@company.com';
```

> This is called a **Covering Index** — the index "covers" every column
> the query needs. Avoids a "Key Lookup" (extra trip back to the table),
> which is a common performance win.

---

## 📌 Filtered Index — Indexing Only Part of a Table

```sql
-- Only index ACTIVE users — smaller, faster index for a common query pattern
CREATE INDEX IX_Users_Active_Email
ON Users (Email)
WHERE IsActive = 1;
```

> Great when most queries only care about a subset of rows (e.g. active
> records) — the index is smaller and faster to maintain than indexing
> the whole table.

## 📌 Viewing Existing Indexes

```sql
-- All indexes on a table
EXEC sp_helpindex 'Users';

-- More detail via system views
SELECT i.name AS IndexName, i.type_desc, c.name AS ColumnName
FROM sys.indexes i
INNER JOIN sys.index_columns ic ON i.object_id = ic.object_id AND i.index_id = ic.index_id
INNER JOIN sys.columns c ON ic.object_id = c.object_id AND ic.column_id = c.column_id
WHERE i.object_id = OBJECT_ID('Users');
```

## 📌 Dropping and Rebuilding Indexes

```sql
-- Remove an index
DROP INDEX IX_Users_Email ON Users;

-- Rebuild (defragment) — indexes get fragmented over time as data changes
ALTER INDEX IX_Users_Email ON Users REBUILD;

-- Reorganize — lighter-weight than a full rebuild
ALTER INDEX IX_Users_Email ON Users REORGANIZE;

-- Rebuild ALL indexes on a table
ALTER INDEX ALL ON Users REBUILD;
```

## 📌 The Cost of Indexes — Not Always a Free Win

| Benefit                                        | Cost                                                          |
| ---------------------------------------------- | ------------------------------------------------------------- |
| Faster SELECT/WHERE/JOIN/ORDER BY              | Slower INSERT/UPDATE/DELETE (index must update too)           |
| Faster lookups on large tables                 | More disk space used                                          |
| Enables Covering Indexes (avoid table lookups) | More indexes = more maintenance overhead (rebuild/reorganize) |

> 🔑 **Rule of thumb:** index columns that are frequently used in
> `WHERE`, `JOIN`, and `ORDER BY` — but avoid over-indexing tables with
> heavy write traffic, since every extra index adds overhead to every
> INSERT/UPDATE/DELETE.

---

## 📌 When SQL Server Might NOT Use Your Index

| Reason                                 | Explanation                                                                                                    |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Small table                            | Table Scan can be cheaper than an Index Seek + lookup for a tiny table                                         |
| Function wrapped around indexed column | `WHERE YEAR(CreatedAt) = 2026` can't use an index on `CreatedAt` efficiently — rewrite as a range instead |
| Leading wildcard in LIKE               | `WHERE Email LIKE '%company.com'` can't seek — only `LIKE 'sumit%'` (no leading `%`) can                |
| Outdated statistics                    | SQL Server's row-count estimates are stale — run`UPDATE STATISTICS`                                         |
| Implicit conversion                    | Comparing a column to a different data type can silently disable index usage                                   |

```sql
-- ❌ Can't use index efficiently — function wraps the column
SELECT * FROM Users WHERE YEAR(CreatedAt) = 2026;

-- ✅ Index-friendly — a proper range instead
SELECT * FROM Users WHERE CreatedAt >= '2026-01-01' AND CreatedAt < '2027-01-01';
```

## ❓ Interview Questions

**Q: What is an index and why does it speed up queries?**
A: An index is a separate data structure that maintains a sorted (or otherwise organized) reference to table rows, letting SQL Server locate matching rows directly (an Index Seek) instead of scanning every row in the table (a Table Scan).

**Q: What's the "leftmost prefix" rule for composite indexes?**
A: A multi-column index is only efficiently usable when the query's filter starts from the leftmost column(s) of the index, in order — filtering only on a later column in the index (skipping the first) generally can't use it effectively.

**Q: What is a Covering Index?**
A: An index that includes (via the base key or an INCLUDE clause) every column a specific query needs, so the query can be satisfied entirely from the index without an extra lookup back to the actual table data.

**Q: Why shouldn't you index every column on every table?**
A: Every index speeds up reads but adds overhead to every INSERT, UPDATE, and DELETE (since the index has to be maintained too), plus extra disk space and maintenance (rebuild/reorganize) cost — indexes should be added deliberately based on actual query patterns, not blindly.
