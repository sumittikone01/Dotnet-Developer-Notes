
# 44.MERGE / Upsert

---

## 📌 What is MERGE

> **MERGE** is a T-SQL statement that combines **INSERT, UPDATE, and DELETE**
> into a single statement — comparing a source and a target, then deciding
> row-by-row what to do.

- Also called an **"Upsert"** = **UP**date + in**SERT**
- Used when: you get a batch of new/changed data and need to sync it into a table
- Without MERGE, you'd write 3 separate statements (INSERT if not exists, UPDATE if exists, DELETE if removed) — MERGE does all 3 in one pass

```
Without MERGE (old way):
──────────────────────────────────────────
IF EXISTS (...) UPDATE ...
ELSE INSERT ...
→ 2 passes over the table, more code, race conditions possible

With MERGE (one statement):
──────────────────────────────────────────
MERGE compares Source vs Target
   → row matches       → UPDATE
   → row is new         → INSERT
   → row missing from source → DELETE (optional)
```

---

## 📌 Basic Syntax

```sql
MERGE INTO TargetTable AS T
USING SourceTable AS S
ON T.KeyColumn = S.KeyColumn

WHEN MATCHED THEN
    UPDATE SET T.Column1 = S.Column1, T.Column2 = S.Column2

WHEN NOT MATCHED BY TARGET THEN
    INSERT (Column1, Column2) VALUES (S.Column1, S.Column2)

WHEN NOT MATCHED BY SOURCE THEN
    DELETE;
```

| Clause                         | Meaning                                                           |
| ------------------------------ | ----------------------------------------------------------------- |
| `USING SourceTable`          | The incoming/new data (table, view, or subquery)                  |
| `ON T.Key = S.Key`           | How to match rows between target and source                       |
| `WHEN MATCHED`               | Row exists in**both** → usually UPDATE                     |
| `WHEN NOT MATCHED BY TARGET` | Row exists in source but**not** in target → INSERT         |
| `WHEN NOT MATCHED BY SOURCE` | Row exists in target but**not** in source → usually DELETE |

> ⚠️ **MERGE must end with a semicolon `;`** — it's one of the few T-SQL statements where this is mandatory.

## 📌 Real Example — Syncing Users from a Staging Table

```sql
-- StagingUsers = fresh data pulled from HR system today
-- Users        = your actual production table

MERGE INTO Users AS T
USING StagingUsers AS S
ON T.UserId = S.UserId

WHEN MATCHED THEN
    UPDATE SET
        T.Role       = S.Role,
        T.Email      = S.Email,
        T.IsActive   = S.IsActive

WHEN NOT MATCHED BY TARGET THEN
    INSERT (UserId, PasswordHash, Role, Email, IsActive)
    VALUES (S.UserId, S.PasswordHash, S.Role, S.Email, S.IsActive)

WHEN NOT MATCHED BY SOURCE THEN
    DELETE;
```

**What happens:**

- Existing users → their Role/Email/IsActive get refreshed
- New users in staging → get inserted
- Users no longer in staging (e.g. left the company) → get deleted

## 📌 Using UPDATE-only / INSERT-only (Skip DELETE)

Most of the time you **don't** want the `DELETE` branch — it's dangerous
(a bad source file could wipe your whole table). Just leave it out:

```sql
-- Safer version — only insert new, update existing, never delete
MERGE INTO Users AS T
USING StagingUsers AS S
ON T.UserId = S.UserId

WHEN MATCHED THEN
    UPDATE SET T.Role = S.Role, T.Email = S.Email

WHEN NOT MATCHED BY TARGET THEN
    INSERT (UserId, PasswordHash, Role, Email)
    VALUES (S.UserId, S.PasswordHash, S.Role, S.Email);
    -- no WHEN NOT MATCHED BY SOURCE → nothing gets deleted
```

---

## 📌 MERGE with a Condition on MATCHED

You can add extra conditions to `WHEN MATCHED` — useful to avoid
unnecessary updates (e.g. only update if something actually changed):

```sql
MERGE INTO Users AS T
USING StagingUsers AS S
ON T.UserId = S.UserId

WHEN MATCHED AND T.Email <> S.Email THEN
    UPDATE SET T.Email = S.Email

WHEN NOT MATCHED BY TARGET THEN
    INSERT (UserId, PasswordHash, Email)
    VALUES (S.UserId, S.PasswordHash, S.Email);
```

> Only rows where the email actually changed get touched — reduces
> unnecessary writes and trigger firing.

---

## 📌 MERGE Using a Subquery as Source

The source doesn't have to be a real table — it can be a query:

```sql
MERGE INTO Users AS T
USING (
    SELECT UserId, Role, Email
    FROM ExternalHRSystem
    WHERE Department = 'IT'
) AS S
ON T.UserId = S.UserId

WHEN MATCHED THEN
    UPDATE SET T.Role = S.Role, T.Email = S.Email

WHEN NOT MATCHED BY TARGET THEN
    INSERT (UserId, Role, Email)
    VALUES (S.UserId, S.Role, S.Email);
```

## 📌 Capturing What MERGE Did — OUTPUT Clause

`OUTPUT` lets you see exactly which rows were inserted/updated/deleted:

```sql
MERGE INTO Users AS T
USING StagingUsers AS S
ON T.UserId = S.UserId

WHEN MATCHED THEN
    UPDATE SET T.Role = S.Role

WHEN NOT MATCHED BY TARGET THEN
    INSERT (UserId, Role) VALUES (S.UserId, S.Role)

OUTPUT $action, inserted.UserId, deleted.UserId;
```

| $action value | Meaning          |
| ------------- | ---------------- |
| `'INSERT'`  | Row was inserted |
| `'UPDATE'`  | Row was updated  |
| `'DELETE'`  | Row was deleted  |

## 📌 The Old Way (Before MERGE) — For Comparison

```sql
-- Manual upsert without MERGE — 2 statements, 2 passes
IF EXISTS (SELECT 1 FROM Users WHERE UserId = 'sumit')
BEGIN
    UPDATE Users SET Role = 'Admin' WHERE UserId = 'sumit';
END
ELSE
BEGIN
    INSERT INTO Users (UserId, Role) VALUES ('sumit', 'Admin');
END
```

> This pattern still works fine for **single-row** upserts. Use `MERGE`
> when syncing a **batch** (many rows) at once — that's where it shines.

## 📌 Common Pitfalls

| Pitfall                                                    | Fix                                                                 |
| ---------------------------------------------------------- | ------------------------------------------------------------------- |
| Forgetting the semicolon`;` at the end                   | Always terminate MERGE with`;`                                    |
| Using`WHEN NOT MATCHED BY SOURCE THEN DELETE` carelessly | Can wipe rows if source table is empty/wrong — test first          |
| Matching on a non-unique column                            | `ON` should use a key that uniquely identifies a row (usually PK) |
| Complex MERGE with triggers                                | MERGE can behave unexpectedly with triggers — test carefully       |

## ❓ Interview Questions

**Q: What is MERGE used for?**
A: To combine INSERT, UPDATE, and DELETE into a single statement by comparing a source dataset against a target table — commonly called an "Upsert" when only INSERT+UPDATE are used.

**Q: What's the difference between `WHEN NOT MATCHED BY TARGET` and `WHEN NOT MATCHED BY SOURCE`?**

|                           | Meaning                         | Typical Action |
| ------------------------- | ------------------------------- | -------------- |
| `NOT MATCHED BY TARGET` | Row is in source but not target | INSERT         |
| `NOT MATCHED BY SOURCE` | Row is in target but not source | DELETE         |

**Q: Why must MERGE end with a semicolon?**
A: T-SQL requires it as the statement terminator for MERGE — omitting it throws a syntax error, unlike most other statements where the semicolon is optional.

**Q: Is MERGE always better than separate INSERT/UPDATE statements?**
A: Not always — for single-row upserts, a simple `IF EXISTS ... UPDATE ELSE INSERT` is often clearer. MERGE is most valuable for batch syncing many rows from a staging/source table in one operation.
