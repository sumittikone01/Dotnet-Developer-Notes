
# 57.Isolation Levels

---

## 📌 What is an Isolation Level

> An **Isolation Level** controls **how much one transaction can see of
> another transaction's in-progress (uncommitted) changes** — it's a
> trade-off dial between **data accuracy** and **concurrency/performance**.

```
More Isolation  →  Safer data, but transactions block each other more (slower)
Less Isolation  →  Faster/more concurrent, but risk of seeing bad/inconsistent data
```

Set per session (or per query) with:

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;   -- example
```

---

## 📌 The Three Core Problems Isolation Levels Prevent

| Problem                       | What Happens                                                                                                                                                                |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Dirty Read**          | Reading another transaction's**uncommitted** changes — data that might get rolled back                                                                               |
| **Non-Repeatable Read** | Reading the same row twice in one transaction, getting**different values** because another transaction changed it in between                                          |
| **Phantom Read**        | Re-running the same query in one transaction and getting**different rows** (new rows appeared/disappeared) because another transaction inserted/deleted matching rows |

```
Dirty Read example:
──────────────────────────────────────────
T1: UPDATE Balance = 5000 (not committed yet)
T2: SELECT Balance → sees 5000
T1: ROLLBACK (balance was never really 5000!)
→ T2 acted on data that never actually existed
```

---

## 📌 The 5 Isolation Levels (Weakest → Strongest)

| Level                        | Dirty Read   | Non-Repeatable Read | Phantom Read | Locking Behavior                        |
| ---------------------------- | ------------ | ------------------- | ------------ | --------------------------------------- |
| `READ UNCOMMITTED`         | ✅ Possible  | ✅ Possible         | ✅ Possible  | No locks — fastest, riskiest           |
| `READ COMMITTED` (default) | ❌ Prevented | ✅ Possible         | ✅ Possible  | Short-lived locks during read           |
| `REPEATABLE READ`          | ❌ Prevented | ❌ Prevented        | ✅ Possible  | Locks held until transaction ends       |
| `SERIALIZABLE`             | ❌ Prevented | ❌ Prevented        | ❌ Prevented | Range locks — most restrictive         |
| `SNAPSHOT`                 | ❌ Prevented | ❌ Prevented        | ❌ Prevented | No locks — uses row versioning instead |

> 🔑 **`READ COMMITTED` is SQL Server's default** — it prevents dirty
> reads but still allows non-repeatable and phantom reads.

---

## 📌 1. READ UNCOMMITTED — Fastest, Least Safe

```sql
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SELECT * FROM Accounts WHERE AccountId = 'A1';
-- Can see OTHER transactions' uncommitted changes (dirty read)
```

Also achievable per-query with the `NOLOCK` hint:

```sql
SELECT * FROM Accounts WITH (NOLOCK) WHERE AccountId = 'A1';
```

> Used when: you need maximum speed and can tolerate occasionally
> reading slightly-wrong (uncommitted) data — e.g. rough dashboard
> counts where perfect accuracy isn't critical.

---

## 📌 2. READ COMMITTED — The Default

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT * FROM Accounts WHERE AccountId = 'A1';
-- Only sees COMMITTED data — no dirty reads
-- But if you read the same row again later in the same transaction,
-- it might have changed (another transaction committed in between)
```

> Good default balance for most applications — safe from dirty reads,
> reasonable concurrency.

---

## 📌 3. REPEATABLE READ — Locks What You've Read

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

BEGIN TRANSACTION;
    SELECT Balance FROM Accounts WHERE AccountId = 'A1';   -- Balance = 1000
    -- ... other transaction tries to UPDATE this row → BLOCKED until we finish
    SELECT Balance FROM Accounts WHERE AccountId = 'A1';   -- guaranteed still 1000
COMMIT TRANSACTION;
```

> Guarantees that if you read a row twice in the same transaction, you
> get the **same value** both times — because SQL Server locks those
> specific rows until your transaction ends. Still allows **phantom
> rows** — a new row matching your WHERE could still appear.

---

## 📌 4. SERIALIZABLE — Strictest

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

BEGIN TRANSACTION;
    SELECT * FROM Accounts WHERE Balance > 1000;
    -- Locks the ENTIRE RANGE — another transaction can't INSERT
    -- a new row with Balance > 1000 until this transaction ends
    SELECT * FROM Accounts WHERE Balance > 1000;  -- guaranteed identical result
COMMIT TRANSACTION;
```

> Prevents all three problems (dirty, non-repeatable, phantom) by
> locking entire ranges of data — safest, but causes the most blocking
> and lowest concurrency. Use only when correctness absolutely can't
> tolerate any of the three anomalies.

---

## 📌 5. SNAPSHOT — Safe AND Fast (Row Versioning)

```sql
-- Must be enabled at the database level first
ALTER DATABASE LoginDB SET ALLOW_SNAPSHOT_ISOLATION ON;

SET TRANSACTION ISOLATION LEVEL SNAPSHOT;

BEGIN TRANSACTION;
    SELECT * FROM Accounts WHERE AccountId = 'A1';
    -- Sees a consistent "snapshot" of data as of the transaction's START
    -- Other transactions' changes are invisible, and this transaction
    -- does NOT block writers, and writers don't block it
COMMIT TRANSACTION;
```

> Instead of locking, SQL Server keeps a **version** of the row as it
> looked when your transaction started (stored in `tempdb`). Readers
> never block writers and writers never block readers — the best of
> both worlds — at the cost of extra `tempdb` storage and version-chain
> overhead.

---

## 📌 Isolation Levels Compared — Full Picture

| Level                | Blocking Behavior           | Speed          | Safety                    |
| -------------------- | --------------------------- | -------------- | ------------------------- |
| `READ UNCOMMITTED` | None                        | ⚡⚡⚡ Fastest | ❌ Least safe             |
| `READ COMMITTED`   | Minimal (short locks)       | ⚡⚡ Fast      | ⚠️ Default, reasonable  |
| `REPEATABLE READ`  | Moderate (holds read locks) | ⚡ Slower      | ✅ Safer                  |
| `SERIALIZABLE`     | Heavy (range locks)         | 🐢 Slowest     | ✅✅ Safest (locking)     |
| `SNAPSHOT`         | None (versioning instead)   | ⚡⚡ Fast      | ✅✅ Safest (no blocking) |

---

## 📌 Choosing the Right Isolation Level — Rule of Thumb

```
Need maximum speed, tolerate stale/dirty data (dashboards)?
    → READ UNCOMMITTED

Standard business application (most cases)?
    → READ COMMITTED (the default — usually leave it alone)

Need to read the same value twice reliably within one transaction
(e.g. checking a balance before AND after a calculation)?
    → REPEATABLE READ

Need airtight correctness, financial/critical calculations,
can tolerate slower performance?
    → SERIALIZABLE

Need strong consistency WITHOUT blocking readers/writers,
and can afford extra tempdb usage?
    → SNAPSHOT
```

---

## 📌 Checking Current Isolation Level

```sql
DBCC USEROPTIONS;   -- shows current session settings, including isolation level

-- Or query it directly
SELECT CASE transaction_isolation_level
    WHEN 1 THEN 'READ UNCOMMITTED'
    WHEN 2 THEN 'READ COMMITTED'
    WHEN 3 THEN 'REPEATABLE READ'
    WHEN 4 THEN 'SERIALIZABLE'
    WHEN 5 THEN 'SNAPSHOT'
END AS IsolationLevel
FROM sys.dm_exec_sessions
WHERE session_id = @@SPID;
```

## ❓ Interview Questions

**Q: What is the default isolation level in SQL Server, and what does it protect against?**
A: READ COMMITTED is the default. It prevents dirty reads (reading another transaction's uncommitted changes) but still allows non-repeatable reads and phantom reads.

**Q: What's the difference between a non-repeatable read and a phantom read?**
A: A non-repeatable read happens when re-reading the SAME row within a transaction returns a different value because another transaction updated it. A phantom read happens when re-running the SAME query returns a different SET OF ROWS because another transaction inserted or deleted rows matching the query's condition.

**Q: What makes SNAPSHOT isolation different from the locking-based isolation levels?**
A: SNAPSHOT uses row versioning instead of locks — it gives each transaction a consistent view of the data as it existed when the transaction started, stored via versions in tempdb. This means readers never block writers and writers never block readers, unlike REPEATABLE READ or SERIALIZABLE which rely on holding locks.

**Q: When would you choose SERIALIZABLE over READ COMMITTED?**
A: When correctness is critical enough that you cannot tolerate dirty reads, non-repeatable reads, OR phantom reads — e.g., certain financial calculations — and you're willing to accept significantly more blocking and reduced concurrency as the trade-off.
