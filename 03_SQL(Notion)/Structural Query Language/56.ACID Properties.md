
# 56.ACID Properties

---

## 📌 What is ACID

> **ACID** is a set of 4 guarantees a database engine makes about
> **transactions**, ensuring data stays reliable and correct even when
> things go wrong (crashes, concurrent users, power loss).

```
A — Atomicity     → All or nothing
C — Consistency   → Always valid state
I — Isolation     → Transactions don't interfere with each other
D — Durability    → Once committed, it survives a crash
```

> A **transaction** is a group of one or more SQL statements treated as
> a single unit of work — `BEGIN TRANSACTION ... COMMIT` (or `ROLLBACK`).

---

## 📌 A — Atomicity ("All or Nothing")

> Every statement in a transaction either **all succeed together**, or
> **all fail together**. There's no partial completion.

```sql
BEGIN TRANSACTION;

    UPDATE Accounts SET Balance = Balance - 500 WHERE AccountId = 'A1';  -- debit
    UPDATE Accounts SET Balance = Balance + 500 WHERE AccountId = 'A2';  -- credit

    -- If the SECOND statement fails for any reason (constraint, crash,
    -- disk error), the FIRST statement must also be undone —
    -- otherwise money vanishes from A1 without appearing in A2.

COMMIT TRANSACTION;
```

```sql
-- Demonstrating atomicity with TRY/CATCH
BEGIN TRY
    BEGIN TRANSACTION;
        UPDATE Accounts SET Balance = Balance - 500 WHERE AccountId = 'A1';
        UPDATE Accounts SET Balance = Balance + 500 WHERE AccountId = 'A2';
    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    ROLLBACK TRANSACTION;   -- undoes BOTH statements if either failed
    THROW;
END CATCH;
```

> Without atomicity, a crash between the two UPDATEs would leave the
> database in an inconsistent state — money debited from A1 but never
> credited to A2.

---

## 📌 C — Consistency (Always a Valid State)

> A transaction can only move the database from **one valid state to
> another valid state** — it must never violate constraints, data types,
> triggers, or business rules along the way.

```sql
-- Consistency is enforced through constraints
CREATE TABLE Accounts
(
    AccountId NVARCHAR(10) PRIMARY KEY,
    Balance   DECIMAL(10,2) CHECK (Balance >= 0)   -- rule: balance can never go negative
);

BEGIN TRANSACTION;
    UPDATE Accounts SET Balance = Balance - 1000 WHERE AccountId = 'A1';
    -- If this would make Balance negative, the CHECK constraint
    -- rejects it — the transaction can't commit an invalid state
COMMIT TRANSACTION;
```

> Consistency is less something you "code for transaction handling" and
> more the **result** of Atomicity + your constraints/rules being correct.
> If any rule (PK, FK, CHECK, trigger) is violated, the whole transaction
> fails — keeping the database consistent.

---

## 📌 I — Isolation (Transactions Don't Interfere)

> Concurrent transactions should behave as if they ran **one at a time**,
> even though they're actually running simultaneously — each transaction
> shouldn't see another transaction's uncommitted changes.

```sql
-- Transaction 1 (User A)                    -- Transaction 2 (User B) — runs at the SAME time
BEGIN TRANSACTION;                            BEGIN TRANSACTION;
UPDATE Accounts SET Balance = 5000
WHERE AccountId = 'A1';
-- (not committed yet)
                                               SELECT Balance FROM Accounts
                                               WHERE AccountId = 'A1';
                                               -- Should User B see 5000 (uncommitted)
                                               -- or the OLD value? Isolation level decides.
COMMIT TRANSACTION;
```

> Isolation is controlled by **Isolation Levels** (READ UNCOMMITTED,
> READ COMMITTED, REPEATABLE READ, SERIALIZABLE, SNAPSHOT) — covered in
> detail in the next note, since it's a big enough topic on its own.

---

## 📌 D — Durability (Survives a Crash)

> Once a transaction is **committed**, its changes are permanent —
> guaranteed to survive a server crash, power loss, or restart.

```
COMMIT happens →  SQL Server writes to the Transaction Log FIRST
                   (write-ahead logging), then to disk
                →  Server crashes 1 second later
                →  On restart, SQL Server replays the log
                →  Your committed data is still there — guaranteed
```

```sql
BEGIN TRANSACTION;
    UPDATE Accounts SET Balance = Balance + 500 WHERE AccountId = 'A2';
COMMIT TRANSACTION;
-- The instant COMMIT succeeds, this change is durable —
-- even an immediate power failure won't lose it.
```

> This is achieved through **write-ahead logging (WAL)** — SQL Server
> writes the change to the transaction log (`.ldf` file) before
> confirming the COMMIT, so it can always recover to the last committed
> state even after an unexpected shutdown.

## 📌 ACID Summary Table

| Property              | Guarantees                                                      | Enforced by                                           |
| --------------------- | --------------------------------------------------------------- | ----------------------------------------------------- |
| **Atomicity**   | All statements succeed, or none do                              | `BEGIN TRAN` / `COMMIT` / `ROLLBACK`, TRY/CATCH |
| **Consistency** | Data always follows defined rules                               | Constraints (PK, FK, CHECK, NOT NULL), triggers       |
| **Isolation**   | Concurrent transactions don't corrupt each other's view of data | Isolation Levels, locking                             |
| **Durability**  | Committed data survives crashes                                 | Write-ahead transaction log                           |

## 📌 Real-World Example — Money Transfer (All 4 Properties at Once)

```sql
CREATE PROCEDURE sp_TransferMoney
    @FromAccount NVARCHAR(10),
    @ToAccount NVARCHAR(10),
    @Amount DECIMAL(10,2)
AS
BEGIN
    SET NOCOUNT ON;

    BEGIN TRY
        BEGIN TRANSACTION;                                    -- Atomicity starts here

            UPDATE Accounts SET Balance = Balance - @Amount
            WHERE AccountId = @FromAccount;                   -- Consistency: CHECK constraint
                                                                -- blocks negative balance

            UPDATE Accounts SET Balance = Balance + @Amount
            WHERE AccountId = @ToAccount;

            -- While this runs, Isolation ensures no other transaction
            -- sees a half-completed transfer

        COMMIT TRANSACTION;                                   -- Durability: now permanent
    END TRY
    BEGIN CATCH
        ROLLBACK TRANSACTION;                                 -- Atomicity: undo everything
        THROW;
    END CATCH
END;
```

## 📌 Why ACID Matters — What Breaks Without It

| Missing Property | What Could Go Wrong                                                                            |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| No Atomicity     | Money debited from one account, never credited to another (crash mid-transfer)                 |
| No Consistency   | Balance goes negative, orphaned foreign key references, broken business rules                  |
| No Isolation     | Two users reading/writing the same row simultaneously see corrupted/partial data (dirty reads) |
| No Durability    | A confirmed "successful" payment vanishes after a server restart                               |

## ❓ Interview Questions

**Q: What does ACID stand for and why does it matter for databases?**
A: Atomicity, Consistency, Isolation, Durability — four guarantees that ensure transactions complete reliably and data stays correct even in the presence of crashes, errors, or concurrent access. Without them, operations like money transfers could leave data in a corrupted or inconsistent state.

**Q: Give a real-world example of Atomicity.**
A: A bank transfer that debits one account and credits another must be all-or-nothing — if the credit step fails after the debit succeeded, Atomicity requires rolling back the debit too, so money doesn't simply disappear.

**Q: How does SQL Server guarantee Durability?**
A: Through write-ahead logging — when a transaction commits, the change is written to the transaction log before the commit is confirmed, so even an immediate crash or power loss can be recovered from by replaying the log on restart.

**Q: Is Consistency something you write code for directly?**
A: Not usually on its own — Consistency is largely a byproduct of Atomicity (all-or-nothing changes) combined with correctly defined constraints, foreign keys, and triggers that enforce your business rules; if any rule is violated, the transaction fails rather than committing an invalid state.
