
# 51.Views

---

## 📌 What is a View

> A **View** is a **saved, named SELECT query** that behaves like a virtual
> table — you can `SELECT` from it just like a real table, but it doesn't
> store data itself (usually). It's stored permanently in the database.

```
Table  → stores actual data on disk
View   → stores a QUERY DEFINITION only, runs it live every time you SELECT from it

CTE    → lives for ONE query, then disappears
View   → lives permanently in the database, reusable across ANY query, ANY session
```

- Created once with `CREATE VIEW`, then reused forever like a table
- Great for: hiding complex JOINs, restricting which columns/rows users see, reusable reporting logic

---

## 📌 Basic Syntax

```sql
CREATE VIEW ViewName AS
SELECT column1, column2
FROM TableName
WHERE condition;
```

```sql
-- Example: a view of only active users, hiding sensitive columns
CREATE VIEW vw_ActiveUsers AS
SELECT UserId, Role, Email, CreatedAt
FROM Users
WHERE IsActive = 1;
```

**Using it — exactly like a table:**

```sql
SELECT * FROM vw_ActiveUsers;
SELECT UserId FROM vw_ActiveUsers WHERE Role = 'Admin';
SELECT COUNT(*) FROM vw_ActiveUsers;
```

> 🔑 Naming convention: many teams prefix views with `vw_` to distinguish
> them from real tables at a glance.

---

## 📌 Why Use Views

| Reason                                 | Example                                                             |
| -------------------------------------- | ------------------------------------------------------------------- |
| **Simplify complex joins**       | Hide a 4-table JOIN behind one simple`SELECT * FROM vw_X`         |
| **Security — restrict columns** | Give a view without`PasswordHash`/`SSN` to app users            |
| **Security — restrict rows**    | A "MyOrders" view filtered to`WHERE UserId = CURRENT_USER`        |
| **Reusability**                  | Write the JOIN logic once, reuse everywhere instead of copy-pasting |
| **Backward compatibility**       | If a table's structure changes, a view can keep old code working    |

```sql
-- Example: hiding a complex join behind a simple view
CREATE VIEW vw_UserOrderSummary AS
SELECT
    U.UserId,
    U.Email,
    COUNT(O.OrderId) AS TotalOrders,
    SUM(O.Amount)    AS TotalSpent
FROM Users U
LEFT JOIN Orders O ON O.UserId = U.UserId
GROUP BY U.UserId, U.Email;

-- Now anyone can just do:
SELECT * FROM vw_UserOrderSummary WHERE TotalSpent > 10000;
-- instead of writing the JOIN + GROUP BY every time
```

## 📌 Modifying a View — ALTER VIEW

```sql
-- SQL Server has no "CREATE OR ALTER" issue if you use this syntax:
ALTER VIEW vw_ActiveUsers AS
SELECT UserId, Role, Email, CreatedAt, LastLoginAt   -- added a column
FROM Users
WHERE IsActive = 1;
```

```sql
-- Modern shortcut — create if it doesn't exist, replace if it does
CREATE OR ALTER VIEW vw_ActiveUsers AS
SELECT UserId, Role, Email, CreatedAt
FROM Users
WHERE IsActive = 1;
```

> `CREATE OR ALTER` (SQL Server 2016 SP1+) avoids the old two-step of
> checking `IF EXISTS` then `DROP` then `CREATE`.

## 📌 Dropping a View

```sql
DROP VIEW IF EXISTS vw_ActiveUsers;
```

## 📌 Updatable Views — Can You INSERT/UPDATE/DELETE Through a View?

> Yes, but **only under specific conditions**. A view is updatable only if
> it's simple enough for SQL Server to trace changes back to exactly one
> underlying table.

```sql
-- ✅ Updatable — simple, single table, no aggregates
CREATE VIEW vw_ActiveUsers AS
SELECT UserId, Role, Email FROM Users WHERE IsActive = 1;

UPDATE vw_ActiveUsers SET Role = 'Admin' WHERE UserId = 'sumit';   -- ✅ works
-- this actually updates the underlying Users table
```

```sql
-- ❌ NOT updatable — has a JOIN, GROUP BY, aggregate function
CREATE VIEW vw_UserOrderSummary AS
SELECT U.UserId, COUNT(O.OrderId) AS TotalOrders
FROM Users U LEFT JOIN Orders O ON O.UserId = U.UserId
GROUP BY U.UserId;

UPDATE vw_UserOrderSummary SET TotalOrders = 5;   -- ❌ ERROR
```

| A view is NOT updatable if it contains...             |
| ----------------------------------------------------- |
| `JOIN` across multiple tables                       |
| `GROUP BY` / aggregate functions (SUM, COUNT, etc.) |
| `DISTINCT`                                          |
| `UNION`                                             |
| Certain subqueries                                    |

## 📌 WITH CHECK OPTION — Preventing "Invisible" Rows

> Without `CHECK OPTION`, you could `INSERT`/`UPDATE` through a view in a
> way that makes the row **no longer match the view's own WHERE clause**
> — the row disappears from the view immediately after you touch it.

```sql
CREATE VIEW vw_ActiveUsers AS
SELECT UserId, Role, Email, IsActive
FROM Users
WHERE IsActive = 1
WITH CHECK OPTION;

-- Without CHECK OPTION, this would silently succeed and the row
-- would vanish from vw_ActiveUsers (since IsActive is now 0)
UPDATE vw_ActiveUsers SET IsActive = 0 WHERE UserId = 'sumit';
-- ❌ WITH CHECK OPTION blocks this — error, because it violates the view's own WHERE
```

## 📌 SCHEMABINDING — Locking the View to the Table Structure

```sql
CREATE VIEW vw_ActiveUsers
WITH SCHEMABINDING AS
SELECT UserId, Role, Email
FROM dbo.Users        -- must use 2-part name (schema.table) with SCHEMABINDING
WHERE IsActive = 1;
```

- Prevents the underlying table's columns (used by the view) from being
  altered or dropped while the view depends on them
- **Required** if you want to create an **Indexed View** (see below)

```sql
-- ❌ WILL FAIL — Email column is used by a schemabound view
ALTER TABLE Users DROP COLUMN Email;
-- Error: cannot drop column, object 'vw_ActiveUsers' depends on it
```

## 📌 Indexed Views (Materialized Views)

> A normal view runs its query **live, every time**. An **Indexed View**
> actually **stores** the result physically (like a table) and keeps it
> updated automatically — trading write-speed for read-speed.

```sql
CREATE VIEW vw_OrderTotals
WITH SCHEMABINDING AS
SELECT UserId, SUM(Amount) AS TotalAmount, COUNT_BIG(*) AS OrderCount
FROM dbo.Orders
GROUP BY UserId;

-- Create a UNIQUE CLUSTERED INDEX to materialize it
CREATE UNIQUE CLUSTERED INDEX IX_vw_OrderTotals
ON vw_OrderTotals (UserId);
```

|                                         | Regular View                | Indexed View                         |
| --------------------------------------- | --------------------------- | ------------------------------------ |
| Data physically stored                  | ❌ No — runs query live    | ✅ Yes — stored like a table        |
| Read speed                              | Depends on underlying query | ⚡ Fast — pre-computed              |
| Write speed on base tables              | Not affected                | Slightly slower — index must update |
| Requires`SCHEMABINDING`               | ❌ No                       | ✅ Yes                               |
| Requires`COUNT_BIG(*)` if using COUNT | ❌ No                       | ✅ Yes (not`COUNT(*)`)             |

## 📌 View vs Table vs CTE — Quick Comparison

|                          | View                      | Table     | CTE       |
| ------------------------ | ------------------------- | --------- | --------- |
| Stores actual data       | ❌ No (unless indexed)    | ✅ Yes    | ❌ No     |
| Lifespan                 | Permanent                 | Permanent | One query |
| Reusable across sessions | ✅ Yes                    | ✅ Yes    | ❌ No     |
| Can be indexed           | ⚠️ Only as Indexed View | ✅ Yes    | ❌ No     |

## 📌 Common Pitfalls

| Pitfall                                                    | Fix                                                                                        |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Expecting a view to be "faster" automatically              | It's not — it just saves the query text; performance = the underlying query's performance |
| Trying to UPDATE through a multi-table/aggregate view      | Not allowed — update the base table directly, or use`INSTEAD OF` triggers               |
| Forgetting`WITH CHECK OPTION`                            | Rows can silently vanish from a filtered view after an update                              |
| Dropping/renaming a column used by a`SCHEMABINDING` view | Blocked — must alter/drop the view first                                                  |

## ❓ Interview Questions

**Q: What is a View, and does it store data?**
A: A View is a saved SELECT query that acts like a virtual table. By default it does NOT store data — it re-runs the underlying query every time it's selected from. An Indexed View is the exception, since it physically stores and maintains the result.

**Q: Can you always INSERT/UPDATE/DELETE through a view?**
A: No — only "simple" views (single table, no JOIN, no GROUP BY/aggregates, no DISTINCT or UNION) are updatable. Complex views require updating the base tables directly or using INSTEAD OF triggers.

**Q: What does WITH CHECK OPTION do?**
A: It prevents an INSERT or UPDATE performed through the view from creating a row that would no longer satisfy the view's own WHERE clause — without it, such a row would just silently disappear from the view.

**Q: What's the difference between a regular View and an Indexed View?**
A: A regular view always runs its query live against the base tables. An Indexed View physically stores the result set (via a unique clustered index) and SQL Server keeps it in sync automatically — trading some write overhead for much faster reads. It requires SCHEMABINDING.
