
# Normalization: 1NF, 2NF, 3NF

---

## 📌 What is Normalization

> **Normalization** is the process of organizing tables to **reduce data
> redundancy** and **avoid update anomalies** — by splitting data into
> multiple related tables instead of cramming everything into one.

```
Unnormalized data:
──────────────────────────────────────────
One giant table, data repeated everywhere,
same fact stored in multiple places → update ONE place, forget the
others → data becomes inconsistent

Normalized data:
──────────────────────────────────────────
Data split into focused tables, each fact stored ONCE,
related via foreign keys → update ONE place, done, everything consistent
```

- Applied through a series of **Normal Forms** (1NF, 2NF, 3NF, and beyond)
- Each level builds on the previous one — you can't be in 3NF without
  first satisfying 2NF and 1NF
- Trade-off: more normalization = less redundancy, but often more JOINs

---

## 📌 The Problems Normalization Prevents — Anomalies

| Anomaly                  | What Happens                                                                                                               |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| **Update Anomaly** | Same fact stored in multiple rows — update one, forget the others, data becomes inconsistent                              |
| **Insert Anomaly** | Can't add certain data without also having unrelated data (e.g. can't add a new Department until an Employee exists in it) |
| **Delete Anomaly** | Deleting one row accidentally destroys unrelated information stored in the same row                                        |

## 📌 Starting Point — An Unnormalized Table

```
Orders (BEFORE normalization):
──────────────────────────────────────────────────────────────────
OrderId | CustomerName | CustomerEmail    | ProductNames         | ProductPrices
1       | Sumit         | sumit@x.com      | Mouse, Keyboard      | 500, 1200
2       | Sumit         | sumit@x.com      | Monitor               | 8000
```

**Problems already visible:**

- `CustomerName`/`CustomerEmail` repeated for every order (redundancy)
- `ProductNames`/`ProductPrices` store MULTIPLE values in one cell
  (violates the most basic rule — this is what 1NF fixes)

---

## 📌 1NF — First Normal Form

> **Rule:** Every column must hold a **single (atomic) value** — no
> repeating groups, no comma-separated lists, no multiple values in one
> cell. Every row must be uniquely identifiable (a primary key).

```
❌ VIOLATES 1NF:
OrderId | ProductNames
1       | Mouse, Keyboard        ← multiple values in ONE cell

✅ SATISFIES 1NF — one row per product instead:
OrderId | ProductName
1       | Mouse
1       | Keyboard
```

```sql
-- 1NF applied
CREATE TABLE OrderItems
(
    OrderId     INT,
    ProductName NVARCHAR(50),
    Price       DECIMAL(10,2)
);
```

```
Full table now, satisfying 1NF (still has redundancy, fixed in 2NF/3NF):
OrderId | CustomerName | CustomerEmail  | ProductName | Price
1       | Sumit         | sumit@x.com    | Mouse       | 500
1       | Sumit         | sumit@x.com    | Keyboard    | 1200
2       | Sumit         | sumit@x.com    | Monitor     | 8000
```

---

## 📌 2NF — Second Normal Form

> **Rule:** Must already satisfy 1NF, AND every non-key column must
> depend on the **ENTIRE primary key** — not just part of it.
> (This rule only matters when the primary key is **composite**, made
> of more than one column.)

```
Table (composite PK = OrderId + ProductName):
OrderId | ProductName | Price | CustomerName | CustomerEmail
1       | Mouse       | 500   | Sumit         | sumit@x.com
1       | Keyboard    | 1200  | Sumit         | sumit@x.com
2       | Monitor     | 8000  | Sumit         | sumit@x.com
```

```
❌ VIOLATES 2NF:
- Price depends on ProductName only (part of the key) — NOT on OrderId
- CustomerName/CustomerEmail depend on OrderId only (part of the key) — NOT on ProductName
- These are "PARTIAL DEPENDENCIES" — non-key columns depending on
  only PART of the composite key, not the whole thing
```

**Fix — split into separate tables, each with its own proper key:**

```sql
-- Orders — CustomerName/Email depend only on OrderId → separate table
CREATE TABLE Orders
(
    OrderId       INT PRIMARY KEY,
    CustomerName  NVARCHAR(50),
    CustomerEmail NVARCHAR(100)
);

-- Products — Price depends only on ProductName → separate table
CREATE TABLE Products
(
    ProductId   INT PRIMARY KEY,
    ProductName NVARCHAR(50),
    Price       DECIMAL(10,2)
);

-- OrderItems — the actual many-to-many link, no partial dependency now
CREATE TABLE OrderItems
(
    OrderId   INT,
    ProductId INT,
    PRIMARY KEY (OrderId, ProductId)
);
```

---

## 📌 3NF — Third Normal Form

> **Rule:** Must already satisfy 2NF, AND no non-key column can depend
> on **another non-key column** (only on the primary key). This is
> called removing **"transitive dependencies."**

```
Orders table (still has an issue):
OrderId | CustomerId | CustomerName | CustomerEmail
1       | C1          | Sumit         | sumit@x.com
2       | C1          | Sumit         | sumit@x.com
```

```
❌ VIOLATES 3NF:
- CustomerName and CustomerEmail depend on CustomerId,
  NOT directly on OrderId (the primary key)
- OrderId → CustomerId → CustomerName   (this chain is a
  "TRANSITIVE DEPENDENCY" — CustomerName depends on OrderId
  only THROUGH CustomerId, not directly)
```

**Fix — pull the transitively-dependent data into its own table:**

```sql
CREATE TABLE Customers
(
    CustomerId    INT PRIMARY KEY,
    CustomerName  NVARCHAR(50),
    CustomerEmail NVARCHAR(100)
);

CREATE TABLE Orders
(
    OrderId    INT PRIMARY KEY,
    CustomerId INT FOREIGN KEY REFERENCES Customers(CustomerId)
    -- CustomerName/Email are GONE from here — look them up via CustomerId
);
```

---

## 📌 Full Before/After — All Three Normal Forms Applied

```
BEFORE (unnormalized):
Orders(OrderId, CustomerName, CustomerEmail, ProductNames, ProductPrices)

AFTER (1NF + 2NF + 3NF):
Customers(CustomerId PK, CustomerName, CustomerEmail)
Products(ProductId PK, ProductName, Price)
Orders(OrderId PK, CustomerId FK)
OrderItems(OrderId FK, ProductId FK, PK(OrderId, ProductId))
```

```sql
-- Querying the normalized structure requires JOINs — this is the trade-off
SELECT
    O.OrderId,
    C.CustomerName,
    P.ProductName,
    P.Price
FROM Orders O
INNER JOIN Customers C ON C.CustomerId = O.CustomerId
INNER JOIN OrderItems OI ON OI.OrderId = O.OrderId
INNER JOIN Products P ON P.ProductId = OI.ProductId;
```

## 📌 Quick Reference — What Each Normal Form Fixes

| Normal Form   | Rule                                                                         | Fixes                                                 |
| ------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------- |
| **1NF** | Atomic values only, no repeating groups                                      | Multiple values crammed into one column               |
| **2NF** | Non-key columns depend on the WHOLE primary key                              | Partial dependency (only matters with composite keys) |
| **3NF** | Non-key columns depend ONLY on the primary key, not on other non-key columns | Transitive dependency (A → B → C chains)            |

```
Easy memory trick:
──────────────────────────────────────────
1NF: "One value per cell"
2NF: "Depend on the WHOLE key"
3NF: "Depend on NOTHING BUT the key"
     (the classic phrase: "the key, the whole key,
      and nothing but the key")
```

## 📌 Normalization vs Denormalization — The Trade-Off

|                   | Normalized (3NF+)                                  | Denormalized                                      |
| ----------------- | -------------------------------------------------- | ------------------------------------------------- |
| Data redundancy   | ✅ Minimal                                         | ❌ Higher                                         |
| Update anomalies  | ✅ Avoided                                         | ❌ Risk of inconsistency                          |
| Query complexity  | ⚠️ More JOINs needed                             | ✅ Simpler, often single-table                    |
| Read performance  | Can be slower (JOINs)                              | Can be faster (no JOINs)                          |
| Write performance | ✅ Faster (update one place)                       | Slower (update multiple copies)                   |
| When to use       | Transactional (OLTP) systems — most business apps | Reporting/analytics (OLAP), read-heavy dashboards |

> 🔑 In practice: **normalize your core transactional tables** (this is
> what 1NF/2NF/3NF gives you), but it's common and acceptable to
> **deliberately denormalize** specific reporting tables/views for
> read performance — as long as it's an intentional trade-off, not an
> accident.

## ❓ Interview Questions

**Q: What problem does normalization solve?**
A: It reduces data redundancy and prevents update/insert/delete anomalies by ensuring each fact is stored in exactly one place, related to other tables via foreign keys, instead of being repeated across many rows.

**Q: What's the difference between 2NF and 3NF in simple terms?**
A: 2NF requires that non-key columns depend on the ENTIRE primary key (this only matters when the key is composite) — it removes partial dependencies. 3NF goes further and requires non-key columns to depend ONLY on the primary key, not on other non-key columns — it removes transitive dependencies (chains like A → B → C).

**Q: What is a transitive dependency? Give an example.**
A: It's when a non-key column depends on another non-key column rather than directly on the primary key — for example, in an Orders table, CustomerName depending on CustomerId, which in turn is just a column on the OrderId-keyed row, rather than CustomerName depending directly on OrderId.

**Q: Is fully normalizing a database always the right choice?**
A: Not always — normalization minimizes redundancy and keeps writes/updates consistent, which is ideal for transactional (OLTP) systems, but it requires more JOINs for reads. For read-heavy reporting/analytics scenarios, deliberately denormalizing (accepting some redundancy) can significantly improve query performance.
