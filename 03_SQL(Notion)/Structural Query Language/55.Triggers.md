# 55.Triggers

---

## 📌 What is a Trigger

> A **Trigger** is special code that runs **automatically** in response
> to an event — an `INSERT`, `UPDATE`, or `DELETE` on a table (or certain
> DDL/login events) — without being explicitly called.

```
Stored Procedure   → runs when YOU call it with EXEC
Trigger              → runs AUTOMATICALLY when a specific event happens
                        (you never call it directly)
```

- Attached to a table (or the whole database/server for DDL/logon triggers)
- Cannot be called manually — fires only when its triggering event occurs
- Used for: auditing, enforcing complex business rules, keeping denormalized data in sync, blocking disallowed changes

---

## 📌 Types of Triggers

| Type                    | Fires on                                         | Common use                              |
| ----------------------- | ------------------------------------------------ | --------------------------------------- |
| **DML Trigger**   | `INSERT`, `UPDATE`, `DELETE` on a table    | Auditing, validation, cascading logic   |
| **DDL Trigger**   | `CREATE`, `ALTER`, `DROP` (schema changes) | Preventing/logging structural changes   |
| **Logon Trigger** | A user logging into SQL Server                   | Restricting logins, connection auditing |

This note focuses on **DML Triggers** — by far the most commonly used.

---

## 📌 AFTER Trigger vs INSTEAD OF Trigger

```
AFTER Trigger:
──────────────────────────────────────────
The actual INSERT/UPDATE/DELETE happens FIRST,
THEN the trigger runs afterward.
(Can't be used on Views.)

INSTEAD OF Trigger:
──────────────────────────────────────────
The trigger REPLACES the action entirely —
the real INSERT/UPDATE/DELETE does NOT happen
unless the trigger explicitly does it itself.
(Commonly used to make Views updatable.)
```

|                                      | AFTER                          | INSTEAD OF                                |
| ------------------------------------ | ------------------------------ | ----------------------------------------- |
| When it runs                         | After the actual DML completes | Instead of the DML — replaces it         |
| Can be used on Views                 | ❌ No                          | ✅ Yes — makes complex views "updatable" |
| Can be used on Tables                | ✅ Yes                         | ✅ Yes                                    |
| Default if you just write`TRIGGER` | `AFTER` (same as `FOR`)    | Must say`INSTEAD OF` explicitly         |

---

## 📌 Basic Syntax — AFTER Trigger

```sql
CREATE TRIGGER TriggerName
ON TableName
AFTER INSERT, UPDATE, DELETE     -- can combine multiple events
AS
BEGIN
    -- trigger logic here
END;
```

## 📌 The Magic Tables — `inserted` and `deleted`

> Inside any DML trigger, SQL Server gives you two special virtual
> tables that hold the affected rows:

| Table        | Contains                                         |
| ------------ | ------------------------------------------------ |
| `inserted` | The**new** values — for INSERT and UPDATE |
| `deleted`  | The**old** values — for DELETE and UPDATE |

```
INSERT  → only `inserted` has rows (the new rows)
DELETE  → only `deleted` has rows (the old rows)
UPDATE  → BOTH have rows — `deleted` = old values, `inserted` = new values
          (matched by the same row's key — this is how you detect "what changed")
```

## 📌 Real Example 1 — Audit Log on UPDATE

```sql
CREATE TABLE UserAuditLog
(
    AuditId    INT IDENTITY PRIMARY KEY,
    UserId     NVARCHAR(50),
    OldRole    NVARCHAR(20),
    NewRole    NVARCHAR(20),
    ChangedAt  DATETIME2 DEFAULT GETDATE()
);

CREATE TRIGGER trg_Users_AuditRoleChange
ON Users
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    -- Only log if Role actually changed
    IF UPDATE(Role)
    BEGIN
        INSERT INTO UserAuditLog (UserId, OldRole, NewRole)
        SELECT D.UserId, D.Role, I.Role
        FROM deleted D
        INNER JOIN inserted I ON D.UserId = I.UserId
        WHERE D.Role <> I.Role;
    END
END;
```

> `UPDATE(ColumnName)` checks whether a specific column was included in
> the UPDATE statement — an efficient way to skip trigger logic when it's
> not relevant.

## 📌 Real Example 2 — Blocking a Disallowed Delete

```sql
CREATE TRIGGER trg_Users_PreventAdminDelete
ON Users
AFTER DELETE
AS
BEGIN
    IF EXISTS (SELECT 1 FROM deleted WHERE Role = 'Admin')
    BEGIN
        RAISERROR ('Cannot delete Admin users.', 16, 1);
        ROLLBACK TRANSACTION;
    END
END;
```

> Since the DELETE already happened when an `AFTER` trigger runs,
> `ROLLBACK TRANSACTION` inside the trigger **undoes** it — this is how
> AFTER triggers enforce "you're not allowed to do that" rules.

## 📌 Real Example 3 — INSTEAD OF Trigger Making a View Updatable

```sql
-- Recall: a view with a JOIN normally can't be updated directly
CREATE VIEW vw_UserProfile AS
SELECT U.UserId, U.Role, P.PhoneNumber
FROM Users U
INNER JOIN UserProfiles P ON P.UserId = U.UserId;

-- INSTEAD OF trigger teaches SQL Server HOW to apply an update
CREATE TRIGGER trg_UserProfile_InsteadOfUpdate
ON vw_UserProfile
INSTEAD OF UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    UPDATE U
    SET U.Role = I.Role
    FROM Users U
    INNER JOIN inserted I ON I.UserId = U.UserId;

    UPDATE P
    SET P.PhoneNumber = I.PhoneNumber
    FROM UserProfiles P
    INNER JOIN inserted I ON I.UserId = P.UserId;
END;
```

```sql
-- Now this works, even though vw_UserProfile spans 2 tables
UPDATE vw_UserProfile SET Role = 'Admin' WHERE UserId = 'sumit';
```

## 📌 Real Example 4 — Keeping a Denormalized Count in Sync

```sql
-- Users.TotalOrders is a denormalized column kept in sync via trigger
CREATE TRIGGER trg_Orders_UpdateUserOrderCount
ON Orders
AFTER INSERT, DELETE
AS
BEGIN
    SET NOCOUNT ON;

    -- Handle inserts — increase count
    UPDATE U
    SET U.TotalOrders = U.TotalOrders + ISNULL(I.OrderCount, 0)
    FROM Users U
    INNER JOIN (SELECT UserId, COUNT(*) AS OrderCount FROM inserted GROUP BY UserId) I
        ON I.UserId = U.UserId;

    -- Handle deletes — decrease count
    UPDATE U
    SET U.TotalOrders = U.TotalOrders - ISNULL(D.OrderCount, 0)
    FROM Users U
    INNER JOIN (SELECT UserId, COUNT(*) AS OrderCount FROM deleted GROUP BY UserId) D
        ON D.UserId = U.UserId;
END;
```

## 📌 ⚠️ Important: Triggers Fire ONCE PER STATEMENT, Not Per Row

> A common beginner mistake: assuming a trigger runs once per affected
> row. It actually runs **once per statement**, but `inserted`/`deleted`
> can contain **multiple rows** if the statement affected multiple rows.

```sql
-- This single UPDATE affects 100 rows
UPDATE Users SET IsActive = 0 WHERE Department = 'IT';

-- The trigger fires ONCE — but `inserted` and `deleted` each contain
-- all 100 rows. Trigger logic MUST be written to handle sets of rows,
-- not just a single row (no "assume one row" logic!).
```

```sql
-- ❌ WRONG — assumes only one row was affected
CREATE TRIGGER trg_Bad ON Users AFTER UPDATE AS
BEGIN
    DECLARE @UserId NVARCHAR(50) = (SELECT UserId FROM inserted);  -- breaks with multiple rows!
    -- ...
END;

-- ✅ CORRECT — always set-based, works for 1 row or 10,000 rows
CREATE TRIGGER trg_Good ON Users AFTER UPDATE AS
BEGIN
    UPDATE U SET U.SomeColumn = I.NewValue
    FROM Users U INNER JOIN inserted I ON I.UserId = U.UserId;
END;
```

## 📌 Managing Triggers

```sql
-- Disable a trigger without deleting it
DISABLE TRIGGER trg_Users_AuditRoleChange ON Users;

-- Re-enable it
ENABLE TRIGGER trg_Users_AuditRoleChange ON Users;

-- Modify
ALTER TRIGGER trg_Users_AuditRoleChange ON Users AFTER UPDATE AS ...;

-- Remove
DROP TRIGGER IF EXISTS trg_Users_AuditRoleChange;

-- See all triggers on a table
SELECT name, is_disabled FROM sys.triggers WHERE parent_id = OBJECT_ID('Users');
```

## 📌 Common Pitfalls

| Pitfall                                                          | Fix                                                                                  |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Writing trigger logic assuming only 1 row changed                | Always write set-based logic using JOINs against`inserted`/`deleted`             |
| Forgetting triggers can cascade (trigger causes another trigger) | Be careful with chained triggers on related tables — can cause unexpected recursion |
| Overusing triggers for logic that belongs in application code    | Reserve triggers for things that MUST happen regardless of caller (audit, integrity) |
| Not knowing a trigger exists (hidden logic surprises developers) | Document triggers clearly — they're invisible unless you check`sys.triggers`      |
| Performance overhead on high-volume tables                       | Every INSERT/UPDATE/DELETE now also runs trigger logic — measure impact             |

## ❓ Interview Questions

**Q: What's the difference between an AFTER trigger and an INSTEAD OF trigger?**
A: An AFTER trigger runs after the actual INSERT/UPDATE/DELETE has already happened and can only be used on tables. An INSTEAD OF trigger replaces the action entirely — the original DML doesn't happen unless the trigger performs it itself — and it can be used on views to make otherwise non-updatable views updatable.

**Q: What are the `inserted` and `deleted` tables inside a trigger?**
A: They're special virtual tables SQL Server populates automatically inside a DML trigger. `inserted` holds the new row values (for INSERT/UPDATE), and `deleted` holds the old row values (for DELETE/UPDATE) — for an UPDATE, matching rows in both tables lets you compare old vs new.

**Q: Does a trigger fire once per row or once per statement?**
A: Once per statement — but `inserted`/`deleted` can contain multiple rows if the statement affected multiple rows. Trigger logic must always be written in a set-based way (using JOINs), never assuming a single row.

**Q: When would you use an INSTEAD OF trigger on a view?**
A: When the view is not naturally updatable (e.g., it joins multiple tables or uses aggregates), an INSTEAD OF trigger lets you define exactly how an INSERT/UPDATE/DELETE against the view should be translated into changes on the underlying base tables.
