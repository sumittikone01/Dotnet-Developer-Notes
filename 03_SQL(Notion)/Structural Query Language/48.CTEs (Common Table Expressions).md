
# 48.CTEs (Common Table Expressions)

---

## 📌 What is a CTE

> A **CTE (Common Table Expression)** is a **temporary, named result set**
> defined with `WITH`, that you can reference like a table **within the
> same query** that follows it.

```
Think of a CTE as a "throwaway view" —
it exists only for the duration of the ONE query right after it,
then disappears. It's not stored anywhere.
```

- Defined using `WITH CteName AS ( ... )`
- Makes complex queries **more readable** than deeply nested subqueries
- Can be **recursive** (a CTE that references itself — for hierarchies)

---

## 📌 Basic Syntax

```sql
WITH CteName AS
(
    SELECT column1, column2
    FROM SomeTable
    WHERE condition
)
SELECT * FROM CteName;
```

```sql
-- Real example: active users only
WITH ActiveUsers AS
(
    SELECT UserId, Role, Email
    FROM Users
    WHERE IsActive = 1
)
SELECT UserId, Role FROM ActiveUsers WHERE Role = 'Admin';
```

> ⚠️ The statement **before** `WITH` must end with a semicolon (if there
> is one), and there can be nothing between the CTE's closing `)` and
> the `SELECT`/`INSERT`/`UPDATE`/`DELETE` that uses it.

---

## 📌 Why Use a CTE Instead of a Subquery

```sql
-- ❌ Nested subquery — hard to read once it gets 2-3 levels deep
SELECT UserId, Role
FROM (
    SELECT UserId, Role, FailedAttempts
    FROM (
        SELECT * FROM Users WHERE IsActive = 1
    ) AS Active
    WHERE FailedAttempts > 3
) AS RiskyUsers;

-- ✅ CTE — same logic, reads top to bottom like a story
WITH ActiveUsers AS (
    SELECT * FROM Users WHERE IsActive = 1
),
RiskyUsers AS (
    SELECT UserId, Role, FailedAttempts
    FROM ActiveUsers
    WHERE FailedAttempts > 3
)
SELECT UserId, Role FROM RiskyUsers;
```

> 🔑 You can chain **multiple CTEs** with commas — each one can reference
> the CTEs defined before it. This is the #1 reason CTEs replace nested
> subqueries in real code — readability.

---

## 📌 CTE vs Subquery vs Temp Table vs View

|                               | CTE            | Subquery             | Temp Table (`#Temp`)     | View                      |
| ----------------------------- | -------------- | -------------------- | -------------------------- | ------------------------- |
| Lifespan                      | One query only | One query only       | Session/connection         | Permanent (until dropped) |
| Reusable across queries       | ❌ No          | ❌ No                | ✅ Yes (within session)    | ✅ Yes (always)           |
| Can be recursive              | ✅ Yes         | ❌ No                | ❌ No (needs looping code) | ❌ No                     |
| Stored in database            | ❌ No          | ❌ No                | ❌ No (temp only)          | ✅ Yes                    |
| Readability for complex logic | ✅ Best        | ❌ Gets messy nested | Good, but heavier          | Good for shared logic     |
| Indexable                     | ❌ No          | ❌ No                | ✅ Yes                     | ⚠️ Only indexed views   |

## 📌 Multiple CTEs Chained Together

```sql
WITH DeptTotals AS
(
    SELECT Department, SUM(Salary) AS TotalSalary
    FROM Employees
    GROUP BY Department
),
CompanyTotal AS
(
    SELECT SUM(Salary) AS GrandTotal FROM Employees
)
SELECT
    D.Department,
    D.TotalSalary,
    C.GrandTotal,
    CAST(D.TotalSalary * 100.0 / C.GrandTotal AS DECIMAL(5,2)) AS PercentOfTotal
FROM DeptTotals D
CROSS JOIN CompanyTotal C;
```

## 📌 Recursive CTE — Handling Hierarchies

> A **recursive CTE** references itself, making it perfect for
> hierarchical data: org charts, category trees, folder structures.

```sql
-- Syntax pattern
WITH CteName AS
(
    -- Anchor member: the starting point (base case)
    SELECT ... FROM Table WHERE condition

    UNION ALL

    -- Recursive member: references CteName itself
    SELECT ... FROM Table
    INNER JOIN CteName ON ...
)
SELECT * FROM CteName;
```

### Real Example — Employee Org Chart

```sql
-- Employees table: EmployeeId, Name, ManagerId (self-referencing FK)

WITH OrgChart AS
(
    -- Anchor: the top-level manager (no manager above them)
    SELECT EmployeeId, Name, ManagerId, 0 AS Level
    FROM Employees
    WHERE ManagerId IS NULL

    UNION ALL

    -- Recursive: find employees reporting to anyone already in OrgChart
    SELECT E.EmployeeId, E.Name, E.ManagerId, O.Level + 1
    FROM Employees E
    INNER JOIN OrgChart O ON E.ManagerId = O.EmployeeId
)
SELECT EmployeeId, Name, Level
FROM OrgChart
ORDER BY Level, Name;
```

**Result — shows the full hierarchy with depth:**

```
EmployeeId | Name          | Level
1          | CEO           | 0
2          | VP Sales      | 1
3          | VP Engineering| 1
4          | Sales Rep A   | 2
5          | Dev A         | 2
```

> 🔑 **How it works:** SQL Server runs the anchor once, then repeatedly
> runs the recursive part — each pass adds one more "generation" — until
> a pass returns zero new rows.

---

## 📌 Preventing Infinite Recursion — MAXRECURSION

```sql
-- Limit to 10 levels deep — SQL Server errors out if it goes further
WITH OrgChart AS
(
    SELECT EmployeeId, Name, ManagerId, 0 AS Level
    FROM Employees WHERE ManagerId IS NULL

    UNION ALL

    SELECT E.EmployeeId, E.Name, E.ManagerId, O.Level + 1
    FROM Employees E
    INNER JOIN OrgChart O ON E.ManagerId = O.EmployeeId
)
SELECT * FROM OrgChart
OPTION (MAXRECURSION 10);
```

> Default `MAXRECURSION` is **100**. Set to `0` for unlimited (risky —
> use only if you're certain the data can't loop, e.g. bad ManagerId data
> pointing back to itself).

## 📌 CTE Used for an Ordered DELETE (Practical Trick)

```sql
-- Delete the oldest 100 audit rows — TOP alone can't ORDER BY in DELETE
WITH OldestLogs AS
(
    SELECT TOP (100) *
    FROM AuditLog
    ORDER BY CreatedAt ASC
)
DELETE FROM OldestLogs;
```

## 📌 CTE Used with ROW_NUMBER() — Removing Duplicates

```sql
-- Keep only the FIRST row per UserId, delete the rest (duplicate cleanup)
WITH RankedRows AS
(
    SELECT *,
        ROW_NUMBER() OVER (PARTITION BY UserId ORDER BY CreatedAt) AS RowNum
    FROM Users
)
DELETE FROM RankedRows
WHERE RowNum > 1;
```

## 📌 Common Pitfalls

| Pitfall                                                | Fix                                                                   |
| ------------------------------------------------------ | --------------------------------------------------------------------- |
| Missing semicolon on the statement BEFORE`WITH`      | Add`;` before `WITH` if there's a prior statement                 |
| Treating CTE as reusable across multiple queries       | It only lives for ONE query — re-declare it if needed again          |
| Infinite recursive CTE (bad self-reference data)       | Set`OPTION (MAXRECURSION n)` and validate data                      |
| Using CTE for performance — expecting it to be cached | CTEs are NOT materialized/cached — same as a subquery under the hood |

## ❓ Interview Questions

**Q: What is a CTE and how long does it live?**
A: A Common Table Expression is a named, temporary result set defined with `WITH`. It only exists for the single query that immediately follows it — it isn't stored and can't be reused in a later query.

**Q: What's the difference between a CTE and a temp table?**
A: A CTE lives only for one query and isn't materialized on disk, while a temp table (`#Temp`) persists for the session/connection, can be indexed, and can be reused across multiple queries.

**Q: How does a recursive CTE work?**
A: It has two parts joined by `UNION ALL` — an anchor member that provides the starting rows, and a recursive member that references the CTE itself to pull the next "level" each pass, stopping when a pass returns no new rows.

**Q: Does using a CTE improve query performance compared to a subquery?**
A: Not inherently — a CTE is generally just syntactic sugar for a subquery; SQL Server's optimizer often produces the same execution plan either way. The main benefit of a CTE is readability, not raw performance.
