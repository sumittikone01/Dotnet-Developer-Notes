
# 47.Correlated Subqueries

---

## 📌 What is a Correlated Subquery

> A **correlated subquery** is a subquery that **references a column from
> the outer query** — meaning it can't run on its own, and it re-runs
> **once per row** of the outer query.

```
Normal (non-correlated) subquery:
──────────────────────────────────────────
Runs ONCE, independently, produces a fixed result,
outer query then uses that result.

Correlated subquery:
──────────────────────────────────────────
Runs ONCE PER ROW of the outer query — like a loop.
Each execution depends on the "current" outer row.
```

---

## 📌 Non-Correlated vs Correlated — Side by Side

```sql
-- ❌ Non-correlated — inner query is independent, runs once
SELECT UserId, Salary
FROM Employees
WHERE Salary > (SELECT AVG(Salary) FROM Employees);

-- ✅ Correlated — inner query references outer table "E1", runs per row
SELECT E1.UserId, E1.Salary, E1.Department
FROM Employees E1
WHERE E1.Salary > (
    SELECT AVG(E2.Salary)
    FROM Employees E2
    WHERE E2.Department = E1.Department   -- ← references outer row
);
```

**What changed:** the inner query now filters by `E1.Department` —
a value that changes depending on which outer row is currently being
checked. That dependency is what makes it "correlated".

|                                 | Non-Correlated | Correlated                   |
| ------------------------------- | -------------- | ---------------------------- |
| Can run standalone?             | ✅ Yes         | ❌ No — needs the outer row |
| Execution                       | Once total     | Once per outer row           |
| References outer query columns? | ❌ No          | ✅ Yes                       |
| Performance (large tables)      | Faster         | Slower (repeated execution)  |

## 📌 Basic Syntax Pattern

```sql
SELECT OuterCol1, OuterCol2
FROM OuterTable AS O
WHERE SomeCondition (
    SELECT InnerCol
    FROM InnerTable AS I
    WHERE I.MatchingColumn = O.MatchingColumn   -- the correlation
);
```

The key giveaway: the inner `WHERE` clause references a column from
the **outer** table alias (`O.MatchingColumn` above).

## 📌 Real Example 1 — Users with Above-Average Failed Attempts in Their Role

```sql
SELECT U1.UserId, U1.Role, U1.FailedAttempts
FROM Users U1
WHERE U1.FailedAttempts > (
    SELECT AVG(U2.FailedAttempts)
    FROM Users U2
    WHERE U2.Role = U1.Role        -- correlated: compares within same Role
);
```

> For every user, this checks: "is your FailedAttempts higher than the
> **average for people with your same Role**?" — the average is
> recalculated per row because it depends on that row's Role.

---

## 📌 Real Example 2 — EXISTS with Correlated Subquery

> `EXISTS` is one of the most common places correlated subqueries appear —
> checking whether **related rows exist** in another table.

```sql
-- Users who have at least one failed login attempt
SELECT U.UserId, U.Role
FROM Users U
WHERE EXISTS (
    SELECT 1
    FROM LoginAttempts LA
    WHERE LA.UserId = U.UserId       -- correlated
      AND LA.Status = 'Failed'
);
```

```sql
-- The opposite — users who have NEVER had a failed attempt
SELECT U.UserId, U.Role
FROM Users U
WHERE NOT EXISTS (
    SELECT 1
    FROM LoginAttempts LA
    WHERE LA.UserId = U.UserId
      AND LA.Status = 'Failed'
);
```

> ⚠️ `SELECT 1` inside `EXISTS` is a convention — the actual column
> selected doesn't matter, since `EXISTS` only checks whether **any row**
> comes back, not the row's content.

---

## 📌 Real Example 3 — Correlated Subquery in SELECT List

Correlated subqueries can also appear as a computed column:

```sql
-- For each user, show their total number of orders
SELECT
    U.UserId,
    U.Role,
    (SELECT COUNT(*) FROM Orders O WHERE O.UserId = U.UserId) AS OrderCount
FROM Users U;
```

> This runs the `COUNT(*)` subquery once **per user row** — for large
> tables, a `JOIN` + `GROUP BY` is usually faster (see comparison below).

---

## 📌 Real Example 4 — Correlated Subquery in UPDATE

```sql
-- Set each user's LastOrderDate to their most recent order
UPDATE U
SET U.LastOrderDate = (
    SELECT MAX(O.OrderDate)
    FROM Orders O
    WHERE O.UserId = U.UserId
)
FROM Users U;
```

## 📌 EXISTS vs IN vs Correlated Subquery — When to Use Which

```sql
-- Using IN — works, but re-checks whole list, doesn't short-circuit
SELECT UserId FROM Users
WHERE UserId IN (SELECT UserId FROM Orders WHERE Status = 'Pending');

-- Using EXISTS — correlated, stops at first match (usually faster)
SELECT UserId FROM Users U
WHERE EXISTS (
    SELECT 1 FROM Orders O
    WHERE O.UserId = U.UserId AND O.Status = 'Pending'
);
```

|                             | IN                                      | EXISTS (correlated)            |
| --------------------------- | --------------------------------------- | ------------------------------ |
| Stops at first match        | ❌ No — builds full list first         | ✅ Yes — short-circuits       |
| NULL handling               | ⚠️ Can behave unexpectedly with NULLs | ✅ Safe with NULLs             |
| Best for                    | Small, fixed lists                      | Checking related-row existence |
| Performance on large tables | Slower                                  | Usually faster                 |

## 📌 Correlated Subquery vs JOIN — Which is Faster?

```sql
-- Correlated subquery version
SELECT U.UserId,
    (SELECT COUNT(*) FROM Orders O WHERE O.UserId = U.UserId) AS OrderCount
FROM Users U;

-- JOIN + GROUP BY version — usually faster for aggregates
SELECT U.UserId, COUNT(O.OrderId) AS OrderCount
FROM Users U
LEFT JOIN Orders O ON O.UserId = U.UserId
GROUP BY U.UserId;
```

> 🔑 **Rule of thumb:** if you're computing an aggregate (COUNT, SUM, AVG)
> per outer row, a `JOIN` + `GROUP BY` is almost always faster than a
> correlated subquery, because the optimizer can process it in one pass
> instead of re-running the subquery per row.
>
> Correlated subqueries still shine for `EXISTS`/`NOT EXISTS` checks and
> row-by-row comparisons (like Example 1 above) where a JOIN would be
> awkward or duplicate rows.

## 📌 Common Pitfalls

| Pitfall                                                       | Fix                                                                       |
| ------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Forgetting the correlation (inner query has no link to outer) | Double-check the inner`WHERE` references the outer alias                |
| Using`IN` with a subquery that can return NULL              | Prefer`EXISTS` — `IN` behaves oddly if the subquery returns any NULL |
| Correlated subquery in SELECT for aggregates on big tables    | Rewrite as`JOIN` + `GROUP BY` for performance                         |
| Confusing table aliases (which is outer, which is inner)      | Name aliases clearly, e.g.`Outer`/`Inner` or `U`/`O` consistently |

## ❓ Interview Questions

**Q: What makes a subquery "correlated"?**
A: It references a column from the outer query, which means it cannot execute independently — it re-runs once for every row processed by the outer query.

**Q: Why is EXISTS often preferred over IN when checking related-row existence?**
A: EXISTS short-circuits as soon as it finds one matching row, and handles NULLs safely. IN builds the full result list from the subquery first and can behave unexpectedly if that list contains NULL values.

**Q: When would you rewrite a correlated subquery as a JOIN?**
A: When the subquery computes an aggregate (COUNT, SUM, AVG) per outer row — a JOIN combined with GROUP BY processes the data in a single pass and generally performs better than re-running the subquery for every row.

**Q: Can a correlated subquery be used in UPDATE or DELETE statements?**
A: Yes — it's common to use one in the SET clause of an UPDATE (to pull a related value like a max date) or in a WHERE/EXISTS clause of a DELETE to remove rows based on related-table conditions.
