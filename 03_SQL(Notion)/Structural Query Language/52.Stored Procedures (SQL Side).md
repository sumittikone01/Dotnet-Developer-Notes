
# 52.Stored Procedures (SQL Side)

---

## 📌 What is a Stored Procedure

> A **Stored Procedure (SP)** is a **saved block of T-SQL code** — one or
> more statements, with optional parameters — that you call by name
> instead of retyping the logic every time.

```
View               → a saved SELECT only (no logic, no parameters)
Stored Procedure    → saved CODE — can SELECT, INSERT, UPDATE, DELETE,
                       loop, branch, accept parameters, return values
```

- Created once with `CREATE PROCEDURE`, called with `EXEC`
- Compiled and cached by SQL Server → generally faster than sending raw
  ad-hoc SQL from the app every time
- Central place for business logic that touches the database

---

## 📌 Basic Syntax

```sql
CREATE PROCEDURE ProcedureName
    @Param1 DataType,
    @Param2 DataType = DefaultValue    -- optional parameter with default
AS
BEGIN
    -- SQL statements here
    SELECT * FROM TableName WHERE Column = @Param1;
END;
```

```sql
-- Example: get a user by UserId
CREATE PROCEDURE sp_GetUserById
    @UserId NVARCHAR(50)
AS
BEGIN
    SELECT UserId, Role, Email, IsActive
    FROM Users
    WHERE UserId = @UserId;
END;
```

**Executing it:**

```sql
EXEC sp_GetUserById @UserId = 'sumit';
-- or positionally
EXEC sp_GetUserById 'sumit';
```

> 🔑 Naming: `sp_` prefix is a common convention, but be aware SQL Server
> reserves `sp_` for **system** procedures — using it for your own SPs can
> cause a tiny lookup slowdown (SQL Server checks `master` DB first).
> Some teams use `usp_` (user stored procedure) instead to avoid this.

## 📌 Parameters — Input, Output, Default Values

```sql
CREATE PROCEDURE sp_ValidateLogin
    @UserId NVARCHAR(50),
    @PasswordHash NVARCHAR(255),
    @IsValid BIT OUTPUT,              -- OUTPUT parameter — returns a value back
    @Role NVARCHAR(20) = 'User' OUTPUT
AS
BEGIN
    IF EXISTS (SELECT 1 FROM Users WHERE UserId = @UserId AND PasswordHash = @PasswordHash)
    BEGIN
        SET @IsValid = 1;
        SELECT @Role = Role FROM Users WHERE UserId = @UserId;
    END
    ELSE
    BEGIN
        SET @IsValid = 0;
    END
END;
```

**Calling with OUTPUT parameters:**

```sql
DECLARE @Valid BIT, @UserRole NVARCHAR(20);

EXEC sp_ValidateLogin
    @UserId = 'sumit',
    @PasswordHash = 'hashed_value',
    @IsValid = @Valid OUTPUT,
    @Role = @UserRole OUTPUT;

SELECT @Valid AS IsValid, @UserRole AS Role;
```

| Parameter type  | Direction                   | Keyword                                |
| --------------- | --------------------------- | -------------------------------------- |
| Input (default) | App → SP                   | just declare normally                  |
| Output          | SP → App (returns a value) | `OUTPUT` on both definition AND call |
| Default value   | Optional if not passed      | `@Param DataType = DefaultValue`     |

## 📌 Variables, IF/ELSE, and Control Flow Inside an SP

```sql
CREATE PROCEDURE sp_LockUserIfTooManyFailures
    @UserId NVARCHAR(50)
AS
BEGIN
    DECLARE @Attempts INT;

    SELECT @Attempts = FailedAttempts FROM Users WHERE UserId = @UserId;

    IF @Attempts >= 5
    BEGIN
        UPDATE Users SET IsLocked = 1 WHERE UserId = @UserId;
        PRINT 'User locked due to too many failed attempts.';
    END
    ELSE
    BEGIN
        PRINT 'User is within allowed attempts.';
    END
END;
```

## 📌 Error Handling — TRY/CATCH

```sql
CREATE PROCEDURE sp_TransferCredits
    @FromUserId NVARCHAR(50),
    @ToUserId NVARCHAR(50),
    @Amount INT
AS
BEGIN
    BEGIN TRY
        BEGIN TRANSACTION;

            UPDATE Users SET Credits = Credits - @Amount WHERE UserId = @FromUserId;
            UPDATE Users SET Credits = Credits + @Amount WHERE UserId = @ToUserId;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        ROLLBACK TRANSACTION;

        DECLARE @ErrorMessage NVARCHAR(4000) = ERROR_MESSAGE();
        THROW 50000, @ErrorMessage, 1;
    END CATCH
END;
```

| Function inside CATCH | Returns                                                  |
| --------------------- | -------------------------------------------------------- |
| `ERROR_MESSAGE()`   | The error text                                           |
| `ERROR_NUMBER()`    | SQL Server error number                                  |
| `ERROR_LINE()`      | Line number where error occurred                         |
| `ERROR_PROCEDURE()` | Name of the procedure where it happened                  |
| `THROW`             | Re-raises an error (modern, preferred over`RAISERROR`) |

## 📌 RETURN vs OUTPUT — Two Ways to Send Data Back

```sql
-- RETURN — only sends back a single INTEGER status code, no result data
CREATE PROCEDURE sp_CheckUserExists
    @UserId NVARCHAR(50)
AS
BEGIN
    IF EXISTS (SELECT 1 FROM Users WHERE UserId = @UserId)
        RETURN 1;
    ELSE
        RETURN 0;
END;

-- Calling it:
DECLARE @Result INT;
EXEC @Result = sp_CheckUserExists @UserId = 'sumit';
SELECT @Result;
```

|                  | RETURN                           | OUTPUT parameter                       |
| ---------------- | -------------------------------- | -------------------------------------- |
| Data type        | Integer only                     | Any data type                          |
| Number of values | One                              | Multiple                               |
| Common use       | Status/error codes (0 = success) | Actual data values (role, count, etc.) |

## 📌 ALTER, DROP, and CREATE OR ALTER

```sql
-- Modify an existing procedure
ALTER PROCEDURE sp_GetUserById
    @UserId NVARCHAR(50)
AS
BEGIN
    SELECT UserId, Role, Email, IsActive, LastLoginAt   -- added a column
    FROM Users
    WHERE UserId = @UserId;
END;

-- Modern shortcut — create if missing, replace if exists
CREATE OR ALTER PROCEDURE sp_GetUserById ...

-- Remove it
DROP PROCEDURE IF EXISTS sp_GetUserById;
```

## 📌 Stored Procedure vs Ad-Hoc Query (from your ASP.NET code)

|                             | Stored Procedure                        | Ad-hoc SQL (built in C#)                   |
| --------------------------- | --------------------------------------- | ------------------------------------------ |
| Execution plan              | Compiled once, cached, reused           | Recompiled more often unless parameterized |
| SQL injection risk          | Low (parameters are separate from code) | Higher risk if string-concatenated         |
| Where logic lives           | Database                                | Application code                           |
| Easier to reuse across apps | ✅ Yes — any app can call it           | ❌ No — tied to that codebase             |
| Version control             | Needs separate DB migration scripts     | Lives with app code naturally              |

```csharp
// Calling a stored procedure from ASP.NET (ADO.NET example)
using (SqlCommand cmd = new SqlCommand("sp_GetUserById", connection))
{
    cmd.CommandType = CommandType.StoredProcedure;
    cmd.Parameters.AddWithValue("@UserId", userId);

    connection.Open();
    SqlDataReader reader = cmd.ExecuteReader();
    // ... read results
}
```

## 📌 Real-World Example — Login Attempt Logic in One SP

```sql
CREATE OR ALTER PROCEDURE sp_AttemptLogin
    @UserId NVARCHAR(50),
    @PasswordHash NVARCHAR(255),
    @Success BIT OUTPUT,
    @Message NVARCHAR(200) OUTPUT
AS
BEGIN
    SET NOCOUNT ON;   -- prevents extra "rows affected" messages from interfering with app code

    IF NOT EXISTS (SELECT 1 FROM Users WHERE UserId = @UserId)
    BEGIN
        SET @Success = 0;
        SET @Message = 'User not found.';
        RETURN;
    END

    IF EXISTS (SELECT 1 FROM Users WHERE UserId = @UserId AND IsLocked = 1)
    BEGIN
        SET @Success = 0;
        SET @Message = 'Account is locked.';
        RETURN;
    END

    IF EXISTS (SELECT 1 FROM Users WHERE UserId = @UserId AND PasswordHash = @PasswordHash)
    BEGIN
        UPDATE Users SET FailedAttempts = 0, LastLoginAt = GETDATE() WHERE UserId = @UserId;
        SET @Success = 1;
        SET @Message = 'Login successful.';
    END
    ELSE
    BEGIN
        UPDATE Users SET FailedAttempts = FailedAttempts + 1 WHERE UserId = @UserId;

        UPDATE Users SET IsLocked = 1
        WHERE UserId = @UserId AND FailedAttempts + 1 >= 5;

        SET @Success = 0;
        SET @Message = 'Invalid password.';
    END
END;
```

> `SET NOCOUNT ON` at the top is a common best practice — it stops
> SQL Server from sending "(1 row affected)" messages after every
> statement, which can confuse ADO.NET result processing.

## ❓ Interview Questions

**Q: What is a Stored Procedure and why use one over ad-hoc SQL?**
A: It's a precompiled, named block of T-SQL that can contain logic (branching, loops, error handling) and accept parameters. Benefits include a cached execution plan for better performance, centralized/reusable business logic, and reduced SQL injection risk since parameters are separated from the query text.

**Q: What's the difference between RETURN and an OUTPUT parameter?**
A: RETURN sends back a single integer, typically used as a status/error code. OUTPUT parameters can return any data type and multiple values, making them the right choice for returning actual data (like a role or count) rather than just a status.

**Q: Why use TRY/CATCH with a transaction inside a stored procedure?**
A: To ensure that if any statement fails partway through a multi-step operation, the transaction can be rolled back to avoid partial/inconsistent data changes, while CATCH captures error details (via ERROR_MESSAGE(), etc.) for logging or re-throwing.

**Q: What does `SET NOCOUNT ON` do and why is it commonly used?**
A: It suppresses the "(N rows affected)" messages SQL Server normally sends after each statement. This is commonly added at the top of stored procedures because those extra messages can interfere with how client code (like ADO.NET) processes results.
